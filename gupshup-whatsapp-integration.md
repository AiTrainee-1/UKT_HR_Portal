# Gupshup WhatsApp Integration -UKTextiles HRMS

The HRMS sends WhatsApp messages (salary slips, ID cards, offer/experience/resignation letters, other employee documents, and Reception's "you have a visitor" alert) through **Gupshup's WhatsApp API**, not Meta's Cloud API directly. Gupshup is a WhatsApp Business Solution Provider (BSP) -it still connects your real WhatsApp Business number through Meta underneath, but you never touch Meta's own developer console; everything (number connection, templates, API key) is managed from Gupshup's dashboard.

This replaced a prior direct-Meta-Cloud-API integration in this codebase. If you're looking at old code, docs, or commit history that mentions `WHATSAPP_ACCESS_TOKEN` / `WHATSAPP_PHONE_NUMBER_ID` / Meta Business Manager templates -that's the old path. It no longer exists in the code.

---

## Architecture

```
┌──────────────────┐   template send (form POST, apikey header)   ┌─────────────┐        ┌──────────────┐
│  Django backend   │ ────────────────────────────────────────────▶│  Gupshup    │───────▶│  WhatsApp /  │
│  whatsapp_service │                                                │  API        │        │  employee's  │
│                    │◀──── GET /api/whatsapp/media/<token> ─────── │  (fetches   │        │  phone       │
└──────────────────┘   (public, fetches the PDF/image to attach)   │  the media) │        └──────────────┘
                                                                     └─────────────┘
```

Two things make this different from a typical "call a REST API" integration, both because of how Gupshup's **Access API** (the self-serve tier) works:

1. **No bearer token -an `apikey` header instead.** One static API key per Gupshup app, sent as `apikey: <key>` on every request.
2. **No direct media upload.** Meta's Cloud API lets you `POST` a file and get back a `media_id`. Gupshup's Access API has no equivalent -document/image template messages instead take a **public URL** that Gupshup's own servers fetch the file from. Since salary slips, ID cards, and letters are generated on the fly (never saved as a permanent file), the backend writes the generated bytes to a short-lived database row (`WhatsAppMediaAsset`) and exposes it at `GET /api/whatsapp/media/<token>` -a random, unguessable, unauthenticated URL that expires after 24 hours and is fetched once by Gupshup right after the send request. This endpoint has to be public (no HR login) because Gupshup's servers, not a logged-in browser, are the ones fetching it.

### Code map

| File | Role |
|---|---|
| `backend/api/whatsapp_service.py` | All Gupshup API calls -template sending, phone normalization, media asset storage. Every document-send view calls `send_document()` or `send_text()` here; nothing else talks to Gupshup directly. |
| `backend/api/whatsapp_views.py` | `Settings → WhatsApp` endpoints (status, template CRUD) + the public `whatsapp_media` view Gupshup fetches attachments from. |
| `backend/api/models.py` | `WhatsAppMessageLog` (audit trail, one row per send attempt), `WhatsAppMessageTemplate` (per-document-type template config), `WhatsAppMediaAsset` (the short-lived media store described above). |
| `config/settings.py` | `GUPSHUP_API_KEY` / `GUPSHUP_APP_NAME` / `GUPSHUP_SOURCE_NUMBER` / `WHATSAPP_DEFAULT_COUNTRY_CODE` / `BACKEND_PUBLIC_URL` -all `.env`-only, never stored in the database. |

## 1. Create a Gupshup account and connect your WhatsApp number

1. Go to **gupshup.io** and sign up (business email + phone).
2. In the Gupshup dashboard, create a new **WhatsApp app** (self-serve / Access API tier is enough for this integration -no need for Enterprise/Partner tier).
3. Gupshup walks you through **Embedded Signup**, which connects a real WhatsApp Business number through Meta on Gupshup's behalf:
   - Sign in with the Facebook/Meta Business account that should own the WhatsApp Business number.
   - Either connect an existing WhatsApp Business number or register a new one (it must not already be active on the regular WhatsApp or Business app on a phone -it gets fully migrated to the API).
   - Complete Meta's business verification if prompted (can take anywhere from minutes to a few days for a new Meta Business Manager account).
4. Once approved, note down from the app's dashboard:
   - **Source number** -the WhatsApp Business number now connected to this app, in international format with no `+` (e.g. `919876543210`). This is `GUPSHUP_SOURCE_NUMBER`.
   - **App name** -the name you gave the app when creating it. This is `GUPSHUP_APP_NAME`.
   - **API key** -under the app's API/Keys section. This is `GUPSHUP_API_KEY`. Treat it like a password; it authenticates every send.

## 2. Create and approve message templates

WhatsApp requires every business-initiated message (one that isn't a reply within 24 hours of the customer messaging first) to use a template that's been submitted and approved -this is a WhatsApp platform rule, not a Gupshup-specific one, so it applies no matter which BSP you use.

1. In the Gupshup dashboard, go to **Templates → Create Template**.
2. Pick a category (**Utility** fits every document type this HRMS sends -salary slips, letters, ID cards, visitor alerts; none of these are marketing).
3. Choose a header type matching what you're sending:
   - **Document** header -for Salary Slip, Offer Letter, Experience Letter, Resignation Letter, Other Employee Documents (all PDFs).
   - **Image** header -for the ID Card (sent as a PNG).
   - **None** -for the Visitor Notification (plain text, no attachment).
4. Write the body with numbered placeholders, e.g.:
   > Hi {{1}}, your salary slip for {{2}} is attached. -UKTextiles HR
5. Submit for approval. WhatsApp/Meta typically reviews within a few minutes to a few hours; rejections usually cite marketing-sounding language or a mismatch between the header type and content -edit and resubmit.
6. Once **Approved**, copy the template's **ID** (a UUID-looking string in the Gupshup dashboard's template list) -you'll paste this into the HRMS in step 4 below. Note that Gupshup identifies templates by this ID, not by the name+language pair Meta's own console uses, so there's no separate "language code" to configure in the HRMS.

Suggested templates to create, matching the document types this HRMS already sends:

| HRMS document type | Suggested header | Suggested body |
|---|---|---|
| Salary Slip | Document | `Hi {{1}}, your salary slip for {{2}} is ready. Please find it attached.` |
| ID Card | Image | `Hi {{1}}, here is your employee ID card.` |
| Offer Letter | Document | `Hi {{1}}, congratulations! Please find your offer letter for {{2}} attached.` |
| Experience Letter | Document | `Hi {{1}}, please find your experience letter attached.` |
| Resignation Letter | Document | `Hi {{1}}, please find the acceptance of your resignation, effective {{2}}, attached.` |
| Other Employee Documents | Document | `Hi {{1}}, please find your {{2}} attached.` |
| Visitor Notification | None | `Hi {{1}}, you have a visitor: {{2}} ({{3}}), here for: {{4}}.` |

## 3. Configure `.env`

Add these to `backend/.env` (placeholders already added there -just fill them in):

```bash
GUPSHUP_API_KEY=<your Gupshup app's API key>
GUPSHUP_APP_NAME=<your Gupshup app name>
GUPSHUP_SOURCE_NUMBER=<connected WhatsApp Business number, international format, no +>

# Optional -only if the backend is reachable at a different public host than
# the one Django sees on incoming requests (e.g. behind certain proxies/
# tunnels). Leave commented out for this project's normal on-premise setup.
# BACKEND_PUBLIC_URL=https://api.uktextiles.in
```

Restart the Django server after editing `.env` -these are read once at process start (`config/settings.py`), same as every other credential in this project.

**`GUPSHUP_SOURCE_NUMBER` must be reachable at a public HTTPS domain, not `localhost`.** Gupshup's servers fetch document/image attachments from `https://<your domain>/api/whatsapp/media/<token>` (see Architecture above) -on `localhost` during local development, Gupshup can't reach that URL at all, so document/image sends will fail even with everything else configured correctly (plain-text-only templates, like Visitor Notification, don't need this and will work locally). Test document/image sends against the deployed server (`https://api.uktextiles.in`), not a local dev instance.

## 4. Configure templates in the HRMS

1. Log in to the HR Portal, go to **Settings → WhatsApp**.
2. The top card shows whether credentials are detected (green) or missing (red, with the exact `.env` keys still needed).
3. In **Message Templates**, for each document type: paste the approved template's **Gupshup Template ID** from step 2, optionally jot a **Variable Note** for your own future reference (e.g. `{{1}}=employee name, {{2}}=month/year`), and toggle **Enabled**.
4. A document type with no template ID or left disabled will fail sends with a clear in-app error ("No WhatsApp template configured for 'salary_slip' -set one up in Settings → WhatsApp") rather than silently doing nothing.

## 5. Test it

- Pick any employee with a phone number on file and a real WhatsApp account on that number.
- Send a Visitor Notification first (Reception module, or trigger `whatsapp_service.send_text` directly) -it's the simplest path (no media fetch involved), good for confirming credentials and the template ID are both right.
- Then test a document send (e.g. a salary slip) against the deployed server, per the localhost caveat above.
- Every attempt -success or failure -writes a row to `WhatsAppMessageLog`, visible via Django admin or a direct query, with the exact error message on failure (`No phone number on file`, `No WhatsApp template configured`, or Gupshup's own rejection reason).

## Not implemented (possible future addition)

This integration only **sends**. Gupshup supports webhooks for delivery/read receipts and inbound replies, but nothing in this codebase currently receives them -`WhatsAppMessageLog.status` only ever reflects whether the send request itself was accepted (`sent`) or rejected (`failed`), not whether the message was actually delivered or read. The prior Meta-based integration had the same limitation, so this isn't a regression -just worth knowing if delivery/read tracking is wanted later, since it would mean adding a new `POST /api/whatsapp/webhook` endpoint and pointing Gupshup's dashboard at it.
