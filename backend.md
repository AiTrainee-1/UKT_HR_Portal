# UKTextiles HRMS -Backend

Django REST API for the HR Portal. This is the single backend for three frontends: the HR Portal (`frontend/`, in this repo), the Employee Web App, and the Employee Mobile App -the latter two live in their own separate repositories and are not part of this one, but every business rule described here applies to them equally since they all call this same API.

## 1. Quick Start

**Prerequisites:** Python 3.11+ (dev machines have run on 3.13/3.14 too), PostgreSQL 15+.

```bash
cd backend
python -m venv .venv
      
pip install -r requirements.txt
copy .env.example .env          # then fill in real values -see Section 3
python manage.py migrate
python manage.py runserver 8080
```

API base: `http://localhost:8080/api`
Health check: `GET http://localhost:8080/api/healthz`

### HR Login

Auth is backed by the `hr_users` table (`HRUser` model), not a single hardcoded credential. The **Super Admin's** login is controlled by `ADMIN_USERNAME`/`ADMIN_PASSWORD` in `.env` (the Railway Variables in production): since 2026-11-10 the .env is the single source of truth for it. On every backend start (`ApiConfig._bootstrap_admin_account` in `apps.py` -> `api/super_admin_sync.py`) the Super Admin row is compared with the .env values and updated when they differ (username set to `ADMIN_USERNAME`, password re-hashed when `ADMIN_PASSWORD` no longer matches the stored bcrypt hash, account switched back on); when they match nothing is written. With no Super Admin yet, the user with that username becomes it or a new one is created. Blank values change nothing; a username already used by another HR user is not taken over (logged as an error, password still synced). Only the Super Admin is touched; each change goes in the activity log (never the password). Account Management shows the Super Admin's password as managed by .env (`credentialsFromEnv`) and refuses to change it (400). The login itself is unchanged: `hr_login` checks `hr_users` (case-insensitive username, active only, bcrypt; 5 failures in 15 min lock the username for 15 min; 12 h JWT tied to a revocable LoginSession). Change the .env values and restart the backend (Railway restarts the service when a Variable changes). The Super Admin creates every other HR account (and its role) from **Account Management**; those logins live only in the database. The e2e stack blanks `ADMIN_USERNAME`/`ADMIN_PASSWORD` (playwright.config.ts) so it keeps its own `e2e_admin`.

`migrate` itself only creates the database schema plus a couple of structural defaults the app needs to function (a default "Head Office" branch, default production shift segments) -it never creates login accounts. A one-time historical migration (`0032_seed_legacy_hr_accounts`) used to also seed MD/Director accounts from legacy env vars on cutover day; that cutover finished long ago and the migration is now a permanent no-op, kept only so `manage.py migrate` never creates a login account again on any future database.

## 2. Architecture

```
┌─────────────────────────────────────────────────┐
│                 Company Network (LAN)            │
│                                                   │
│  ┌──────────────┐     ┌──────────────────────┐  │
│  │  Biometric    │────▶│   Django Backend      │  │
│  │  device       │ ZK  │   Port 8080/8000      │  │
│  │  192.168.0.x  │TCP  │                        │  │
│  └──────────────┘4370 │   PostgreSQL           │  │
│                        └─────────┬──────────────┘ │
│                                  │ /api/*          │
│  ┌──────────────┐                │                │
│  │  HR Portal    │───────────────┘                │
│  │  React/Vite   │                                │
│  │  Port 5173    │                                │
│  └──────────────┘                                 │
└─────────────────────────────────────────────────┘

         │ Cloudflare Tunnel (HTTPS) -see deployment-guide.md
         ▼
┌─────────────────────┐
│  Employee Mobile /   │
│  Employee Web App    │
│  (separate repos)    │
└─────────────────────┘
```

- **HR Portal** uses Vite's dev proxy (`/api` → `http://localhost:8080`) in development; in production Nginx proxies `/api/` to Django directly.
- **Employee Mobile/Web apps** connect over the public HTTPS URL (same Django backend, employee JWT tokens instead of HR ones).
- **Biometric device** stays on the LAN -Django reaches it directly, so attendance never depends on the internet being up.

## 4. Modules & Features

Every module is gated per-role by the hierarchical permission system (Section 4.11) -`hidden`/`view`/`edit`, cascading from parent to child modules.

### 4.1 Dashboard
Live attendance summary, pending-action tiles (leave/permission/casual leave/missing punch/resume screening/documents), recruitment snapshot, monthly salary totals, on-demand biometric sync.

### 4.2 Employees
Directory with search/filters/Excel-like bulk view; add/edit; **Production** (daily/weekly wage, segment attendance) vs **Staff** (monthly salary, Strict/Simple attendance); Bulk Upload (separate Staff/Production sheets, a check-first preview, a per-row result report, and an Update-existing-by-code flow for the active and inactive lists of each kind with explicit handling of employees missing from the file); per-employee Documents checklist; Branch/Department/Designation sub-pages; the **Co Emp** tab (the PF / ESI switch, the TDS list and the PF / ESI coverage numbers with Excel / PDF downloads, Section 4.17).

### 4.3 Attendance & Shift Management
The most heavily-configurable area -see Section 6 for full mechanics.
- **Staff:** Strict Mode (all 4 punches, plus lunch-break policing) or Simple Mode (first/last punch only) -both share the same Full/Half-Shift decision.
- **Production:** separate segment-based engine; Sunday is a normal working day (unlike staff).
- **Manage Shift:** validated templates (no overnight shifts, unique names, a shift in use cannot be deleted), a planner (`shift_planner.py`) that previews and applies an assignment for any mix of included/excluded employees, departments and designations with keep-or-reassign for people already on a shift, ending people off a shift from a chosen day, Assigned/Unassigned views, per-employee time overrides.
- **Late Detection & Without Permission policy:** fully HR-configurable free-allowance + slab-table deduction rules (Section 6).
- **Geo Attendance & On-Duty:** geofenced punch-in/out, destination-based field-work sessions with department-head approval and live location tracking.
- **Missing Punch:** employee-submitted forgotten-punch correction (4 slots), HOD/HR approval (Section 4.13).
- **Manual Punch Import:** bulk Excel import for device outages/backfill.
- **Auto Sync Rules, Attendance Search, Report Log, Night Shift Relaxation.** Report Log has three sub-tabs: Monthly Report, Daily Leave Report (absent staff + Informed / Not informed) and Daily Late Report (staff the engine marked late, with shift start, grace, punch-in and minutes late after grace); the daily ones read `GET /api/attendance/report-log?date=`, which carries `firstPunch`, `shiftStart`, `graceMinutes`, `lateDeadline`, `minutesAfterStart`, `minutesLate`, `branchId`, `branchName` and `unitLabel` per row.

### 4.4 Leave & Holiday
Configurable leave types, per-employee/year balances with carry-forward, request approval (HR and/or department head as the approval pipeline says, attributed), Permission requests (also feed the Late Detection pool), Holiday calendar, automatic attendance reflection.

**Request date window** (`api/request_window.py`): on Leave, Permission, Casual Leave and Missing Punch an *employee token* may only request dates in the current month (plus last month from the 1st to the 5th - 2 days until 2026-11-02; a Missing Punch never in the future), enforced server-side in India time with a 400 `request_window_closed`, never for HR; the same rule and 137 shared vectors live in the web/mobile clients and the HR portal's employee page (`tests_request_window.py`).

### 4.5 Casual Leave (CL)
Paid, staff-only, one per calendar month, eligible after 6 months of service. Separate table/flow from Leave/Permission. Approving/rejecting writes the attendance record directly -payroll picks it up automatically.

### 4.6 Recruitment
New Joinees (offer letter + email/WhatsApp), Resignations (department-head then HR approval by default, configurable), Required Roles, Interviews, Resume Screening (spaCy NLP scoring against an HR-defined rule set, explainable per-candidate scoring, 4-stage pipeline; uploaded resumes for non-selected candidates are **auto-purged after 10 days** -see Section 7), Documents (Company Documents theming + per-employee Employee Documents checklist).

### 4.7 Payroll, Salary & Settlement
Full engine for both employment types:
- **Staff:** monthly salary ÷ working days × effective present days (Full/Half Shift), plus Late Detection and Without Permission deduction pools (Section 6).
- **Production:** shift-based, paid on one of three **pay cycles** -Weekly (7 days), BiWeekly (14 days) or Monthly (four weeks, 28 days)- chosen per employee on Employees → Production Employees (`Employee.production_pay_cycle`; an unassigned employee is in no payroll). Each cycle has its own Production Payroll page, period rule and late rules (Settings → Production Payroll). **Not** tied to calendar months, so a given month can span more than one still-unpaid pay period. This is why any "how many employees are pending" figure for Production must count **distinct employees**, not raw Payroll rows -a fix applied to the Payslip list query and the Production Payroll page's KPI card after exactly this miscount was found (August 2026). **Moving an employee between cycles never pays a day twice (2026-11-06, `production_coverage.py`):** a period pays only the days no other payroll row of the employee pays (`Payroll.paid_ranges`, NULL = the whole period; a staff month counts as its calendar month), days no cycle paid because of the move are added to the first payroll on the new cycle as catch-up days, a fully paid period is refused naming the payroll that paid it, and a part period is judged for PF / ESI on 28 / days paid. Generating a Cleared production payroll again keeps it Cleared, like staff. Tests: `tests_production_coverage.py`.
- **Skipped Employees:** a dry-run preview (before generating) of exactly which employees would be skipped and why (no Salary Amount / no Salary Per Shift / zero working days in the period) -surfaced as a KPI card on both Staff and Production Payroll pages. Staff's check runs automatically on page load (~14s for ~120 employees); Production's is click-triggered instead, since its equivalent check is measurably slower (~84s for ~114 employees, since the production engine's per-employee work is heavier) and firing it automatically on every page visit would be a bad tradeoff.
- Deductions: PF and ESI (Co Emp employees only, by the rules of Settings → PF & ESI), TDS (employees on the TDS list only), advances, Late Attendance penalty, Without Permission penalty (PF, ESI and TDS: Section 4.17).
- Full day-by-day breakdown drawer per payroll record.
- **Payroll insights (read-only, October 2026):** the Staff and Production Payroll pages explain what payroll already stored without touching it: `GET /payroll/<id>/details` (one payroll on its own page: profile, money, how each earning and deduction was worked out, the rules it was generated under and whether they changed since, its issues, days, history, Previous / Next), `/payroll/issues` (every issue detected for a month or period, each with the day it was detected on and a specific detail), `/payroll/rules` (the Settings rules plus each employee's own shift, Co Emp / TDS category, PF / ESI / TDS and pay cycle) and `/payroll/salary-statement` (the printed Salary Statement by department). Production has the same four under `/payroll/production/...`. All are `GET`, built from `Payroll` + `SalarySlip.breakdown_details` + the profile + the live settings (never recomputed; a missing settings row is read as defaults, not created), gated by the URL's own permission module (`payroll` / `production_payroll`) and branch-scoped. Each day of `details.days` also carries `marks` (late / permission / excess permission / On-Duty / On-Duty punch / missed punch) from `payroll_day_marks.py`: read-only, five queries for the whole period, read from the attendance day records, approved `EmployeePermission` / `MissingPunchRequest` / `OnDutySession` rows and the punch sources, so they show attendance as it stands now (tests: `tests_payroll_day_marks.py`). Code: `payroll_insights*.py` and `payroll_statement_views.py`; response contract: `frontend/src/lib/api-client/custom-hooks/payroll-insights.ts`; tests: `tests_payroll_insights.py`.
- **Compensation overhaul (October 2026), staff only:** `/hr/compensation` has four tabs (CTC Breakdown, OT Detection, Compensation Leave, History & Reports) and Settings has a Compensation tab; every rule is editable there. The master switch (`PayrollSettings.compensation_feature_enabled`) sits above per-feature switches and effective-from dates in the singleton `CompensationConfig`, and the editable rule tables are `CompensationRule` rows, so nothing already paid is ever judged again. **Type 1** is an automatic, never-paid late-in allowance for the next working day after extra work (default 60 / 90 min → 30, 120 / 150 min → 60 minutes); **Type 2** (more than 150 minutes past the shift end) is assigned by HR by hand, as relaxation (an alternative day in the same month) or payment (shifts x the daily rate, `earnings.otShifts`), by the last punch-out (default until 9 PM 0.25, 12 AM 0.50, 2 AM 0.75, later 1.00). Compensation Leave: A. company-announced late-in / early-out windows (the announced time replaces the shift edge and grace for that date), B. Sunday / holiday work claims raised by HR and approved by the Department Head (new approval workflow `holiday_work`, HOD switch `can_approve_compensation`) into a compensation balance (`CompensationLedger`), C. paid birthday leave (automatic, Present, 1.00). The attendance engine (`compute_day_record`) applies all of it and writes the day marker (`compensation_kind / _minutes / _note`, `ot_extra_minutes`) that every attendance screen and the employee apps draw. Code: `compensation_rules.py` (pure rules), `compensation_engine.py` (database context for the engine), `compensation_apply.py` (relaxation top-up, balance), `overtime.py` (detection), `compensation_views.py`, `compensation_settings_views.py`, `compensation_windows_views.py`, `holiday_work_views.py`, `compensation_birthday_views.py`, `compensation_reports_views.py`, `employee_compensation_views.py` (employee apps), `overtime_scheduler.py` (background detection every 15 minutes), migrations 0118, 0119 and 0120; endpoints in `api-database-reference.md` (Compensation sections); tests `tests_compensation_*.py`, `tests_holiday_work.py`, `tests_employee_compensation.py`, `tests_comp_fix_*.py`. **Since 2026-11-19 (migration 0166) Type 1, Type 2, holiday work and birthdays go through one claim workflow** (employee or HR claims, the Department Head approves) from an effective date on: see Section 4.20; the paragraph above describes the rules days before that date keep.
- **Production shift rules (October 2026), production only:** a production day's `shifts_earned` is now worked out from the owner's table "leave at this time, earn this many shifts" (Day: 10:30 0.25, 12:45 0.50, 15:30 0.75, 17:45 1.00, 20:00 1.50, 22:30 2.00, 00:30 next day 2.50, 05:30 next day 3.00; Night from 21:00: 00:00 next day 0.50, 05:30 next day 1.50; Sunday 17:00 1.00; unpaid breaks tea, lunch, dinner) instead of the four punch times and the 10-minute grace. Staff paths are untouched. It is edited in Settings → Production Shifts (`GET/PUT /production-shift-rules`, `POST /production-shift-rules/preview`, see `api-database-reference.md`; audit module `production_shift_rules`). **Effective-date rule (safety):** the new calculation judges only days on or after `ProductionShiftConfig.rules_effective_from` and only while `rules_enabled`; every earlier day keeps the legacy calculation (`_compute_production` with `punch1..4_time`, the 10-minute `grace_minutes` and `ProductionShiftSegment`) byte for byte, so nothing already paid is re-judged. Migration `0121_production_shift_rules` is additive (eight `rules_*` columns with defaults on `production_shift_config`, tables `production_shift_groups`, `production_shift_rules`, `production_breaks`, an idempotent seed) and seeds `rules_effective_from` as the IST day it ran; NULL means "legacy". **The algorithm** (pure module `production_shift_rules.py`, exact `Fraction` arithmetic, no database inside the calculation): (1) the day's group is chosen by weekday (Sunday: groups for Sunday or every day, otherwise Monday-Saturday or every day) and by the first-punch window that holds the day's FIRST punch, with the nearest start time (circular clock distance) when none does. (2) Each ladder row is a point "left at T, earned V"; between two rows the value grows pro rata with PAID time, where the enabled break windows (tea, lunch, dinner; same for every group) are cut out, so a break is flat, nobody has to punch for it, and the day is capped at the last row's value. (3) The grace (`rules_grace_minutes`, default 5) lets a first punch at or before start + grace count as the start, while a later one loses value at that band's rate and sets `is_late`; an out punch less than the grace before a ladder row snaps up to that row (17:42 earns the 17:45 value, 17:40 does not). (4) The day's punches are grouped by shift day and paired in order (in, out, in, out), the day is the sum of value(out) minus value(in) over the pairs, an odd count ignores the last open punch, one punch earns 0 (`half_shift`, unpaid like the legacy rule), none is `absent`, and punches under 300 seconds after the previous kept one (double taps) are dropped first; the total is then rounded to a QUARTER of a shift (owner 2026-11-18: production shifts and payroll are 0.25, 0.50, 0.75 ... only; the old `rules_rounding_step` column is no longer read, `build_ruleset` always uses `QUARTER`; `rules_rounding_mode` picks the nearest quarter or the quarter reached), limited to the group's top value (taken down to a quarter), lifted to `rules_min_credit` when there is a complete pair, and a total below `rules_full_day_value` is `half_shift`. (5) **Night sessions:** a night worker's closing punch is made the next calendar morning, so the next day's first punch is added to day d as +24 h and removed from d+1 only when ALL hold: d's resolved list has an odd count, the punch is at or before the close-by time (the latest next-day out time among all groups' rows and standard departures plus 90 minutes, 07:00 with the default tables, derived, no setting), it is within `rules_night_session_hours` (default 24) of d's open punch in whole minutes, both days are judged by the new rules (on or after the effective date), neither is a manual override day (`source == "manual"`, kept as HR entered it), and it is not an EARLY ARRIVAL (owner 2026-11-18): when d is a day shift (standard departure on the same day), a punch made from `EARLY_ARRIVAL_MIN` (150 min) before the start of the shift it begins (06:00 for 08:30) is the next day's first punch, unless the worker clocks in again for that shift by its start + grace (then it ended the night's overtime, which stays on d). A night shift (standard departure the next morning) is closed up to the close-by time as before (`RuleSet.arrival_guard`, passed to the resolver by `session_kwargs`). **All of these are settings since 2026-11-18** (migration 0161, Settings -> Production Shifts -> Night and early morning): `rules_early_arrival_enabled` / `rules_early_arrival_minutes` (150), `rules_clock_in_again_enabled` / `rules_clock_in_again_minutes` (15), `rules_night_exit_enabled`, `rules_close_by_enabled` / `rules_close_by_margin_minutes` (90; off = `close_by_s` None, only the hours limit) and `rules_double_tap_enabled` / `rules_double_tap_minutes` (5; off = `tap_gap_s` 0, also used by the Production Daily Punches report's `tap_blocks`); the module constants are only their defaults. (6) The chain is resolved by walking back from the asked day to the first sync point (a day whose first punch cannot have been consumed) and resolving forward from there, at most 62 days back; callers read a 7-day window with their one punch query and add ONE more query only when no sync point lies inside it, so one day, a range and a month always agree. Flags: late = first punch later than start + grace; early leave = last punch earlier than the standard departure minus grace; the result also carries `rule_group` and `rule_note` (returned to reports and the daily list, never stored). **Where it plugs in:** `attendance_final.compute_day_record` / `compute_month_records` / `compute_range_records` (production branch; the pure `production_day_result` and `production_prefetch_for_day` / `production_prefetch_for` serve reports and roster days), so payroll generation (`_generate_production_payroll` reads `compute_range_records`, pay stays sum(`shifts_earned`) x `salary_per_shift` and a period that spans the date mixes both calculations correctly); `payroll_views._production_late_days` (days on or after the date use the day record's own `is_late` / `early_leave`, i.e. group start + grace, earlier days keep the Manage-Shift template check); `attendance_views` (daily list gains `shiftsEarned`, `isLate`, `isEarlyOut`, `ruleGroup`, `ruleNote`, `lastPunchNextDay`; history and search punch lists mark a closing punch `nextDay`); `growth_views` manual override (a production day may reach the table's top value instead of 1.50); the MD portal attendance analytics and `reporting/definitions/attendance_core_data.py` (late / early minutes through `judge_day`); and the Report Center: HR Reports → Production Daily Punches (punches by shift day, columns Shift, Shifts Earned, Late, Early, Rule applied) and Production Shift Rules, both through `reporting/definitions/production_judge.py` (reads only; a report never writes). The legacy `/production-shift-config` and `/production-shift-segments` endpoints stay and describe the days before the date. Tests: `tests_production_shift_rules.py` (engine, hand-computed bands, a random differential test against an independent implementation, query counts), `tests_production_legacy_snapshot.json` (about 900 patterns recorded from the unmodified legacy code), `tests_production_shift_rules_api.py`, `tests_production_consumers.py`, `tests_reporting_production_shift.py`. **Known behaviours:** a stored night day depends on the NEXT morning's punch (`compute_day_record` recomputes auto rows, but a reader of stored rows only can show a night day until it is recomputed), and payroll generated for a period that ends today can miss that night's closing punch.
- Salary Slip: PDF generation, single/bulk download/email/**WhatsApp** (Section 8), Excel export.
- Settlement: advance/loan records with auto-generated repayment schedules, deducted from payroll automatically each cycle.

### 4.13 Approval Workflow Control
One engine, `backend/api/approval_workflow.py`, decides who may approve every request; HR configures it in **User Management → Approval Workflow Control** (`approval_workflow_views.py`, table `approval_workflow_configs`, permission `user_management.approval_workflow`). The full contract (endpoints, the per-request `approval` block, `workflow_disabled`) is in `api-database-reference.md`; the rules in short:

- **Pipeline:** 1–2 ordered steps; a step's responsible role is `hod`, `hr` or both (whoever acts first, only as the single step); mandatory or optional (an optional step is skipped when the next role decides first; the last step is always mandatory); a role appears once. Built-in pipelines reproduce the old behaviour, so nothing changes until HR edits one. Eleven workflows (`DEFINITIONS`); `leave, permission, casual_leave, outpass, missing_punch, on_duty, resignation` are editable, the HR-only ones and `attendance_correction` are fixed; each can be switched OFF (no new requests; requests already waiting can still be decided).
- **Deciding:** modules never route on their own any more. Each module's resolver (`resolve_leave`, `resolve_permission`, `resolve_casual_leave`, `resolve_outpass_request`, `resolve_missing_punch`, `resolve_on_duty_session`, `resolve_resignation`) calls `approval.decide(key, obj, role, decision, actor=...)`, which checks the request is pending and that this role has a turn (`check_can_act`), appends to `approval_trail` and returns an `Outcome` (`advanced` / `approved` / `rejected`); the module then stamps its own fields, saves, and runs its side effects exactly once when the outcome is final, whichever role gave the last approval. Creation endpoints call `approval.require_enabled(key)` (403 `workflow_disabled`); `ApprovalError` + `approval.refusal(exc)` is the one error shape.
- **Position is derived, not stored:** progress lives in `approval_trail` (`None` = a row from before the feature, derived from the old HOD/HR stamps; `[]` = a real empty trail) and the request's position is recomputed against the pipeline in force, so a pending request follows an edited pipeline from where it is. `resync_pending(key)` re-projects the legacy `status` label after an edit (`pending`, `pending_hod`, `pending_hr`, `dept_approved` only mean "waiting for X now") and never approves or rejects anything.
- **Lists and counts** (HOD pending lists and counts, HR dashboards, sidebar badges) use `filter_actionable` / `can_act`, so each role sees a count of what it can decide now. Configs are memoized per request (thread-local) and cleared on `request_started` and on any config save/delete.
- **Behaviour changes to know about:** the leave balance is deducted at the final approval whichever role gives it (the HOD path used to skip it); HR can no longer re-decide a decided outpass; re-deciding a decided leave/permission is a revision that needs HR in the pipeline (comment-only edits always allowed).
- **Tests:** `api/tests_approval_workflow.py` (rule tables, step validation, catalog, config API + permissions, one scenario class per workflow, resync and cache). Browser coverage: `frontend/e2e/approval-workflow.spec.ts` (the page) and `approval-screens.spec.ts` (the HR screens).

### 4.15 One-time codes by WhatsApp and SMS, and SMS Control
Sign-in, forgot-password and first-time activation codes go by **WhatsApp** (Meta's authentication template `hrms_otp`, 6 digits) and / or **SMS through 2Factor.in** (4 digits). Since 2026-11-20 the two channels are **independent**: SMS codes are switched on at **SMS Control** (`/hr/sms-control`, permission module `sms_control`; default off), WhatsApp codes at WhatsApp Control -> OTP; either alone is enough, and with both on the apps let the employee choose. SMS carries codes ONLY (`sms_service.send_otp` is the only send; a test proves no other module calls the 2Factor client). Every other message goes by WhatsApp (Section 8). The full setup (2Factor account, the approved template `UKT_HRMS_OTP` / sender `UKTHRM`, API key, environment, test) is in **`twofactor-sms-otp-integration.md`**. In short:

- **One flow, two independent carriers.** `otp_service.available_channels(purpose)` lists the channels that may deliver a purpose right now (master + purpose switch on, configured and allowed to send; WhatsApp also needs the engine on and `hrms_otp` APPROVED), WhatsApp first; each channel keeps its own switches and limits (`SmsSettings` for SMS, `WhatsAppSettings` plus constants for WhatsApp), and `EmployeeOtp.channel` (migration 0169) records which one a code went by; generation (random digits, salted HMAC, never stored), expiry, single use, attempt limit and purpose binding are shared. The code has **4 digits by SMS** (the 2Factor template says `XXXX`) and **6 by WhatsApp** (`otp_service.CODE_LENGTH`); the length is stored on the row (`EmployeeOtp.code_length`, migration 0125, additive with a database default of 6), so a code issued before HR flips the channel still verifies with the length it was issued with, and verification checks the row's length (a wrong length is a counted wrong guess with the generic sentence, so it reveals nothing about whether a code is live). Four digits are only 10 000 combinations, so the SMS channel is held tighter: at most 5 wrong guesses per code (the SMS Control page allows 3 to 5; a larger saved value is clamped) and at most 10 codes per employee and purpose in any 24 hours (`SMS_MAX_REQUESTS_PER_DAY`, SMS only), on top of the 5 codes an hour: at most 5 x 10 = 50 guesses a day against one account (0.5 %). `GET /auth/login-options` (no cache) answers `otpChannels {login, reset, activate}` and `channels {whatsapp?, sms?}` besides the old `otpChannel` / `codeLength` (the first channel, for old app builds), and `POST /auth/otp/request` takes an optional `channel` and answers `channel`, `codeLength`, `otherChannels` (a channel that is not available: 400 `channel_unavailable` with `availableChannels`). Password login is never locked out. The new code row is created first and the earlier codes are consumed only after the send succeeded: a failed or blocked send deletes the new row and leaves the employee's previous code valid. The cooldown / hourly check and the creation run under a lock on the employee row, so simultaneous requests send one SMS. Password sign-in is never refused (and `login-options` keeps `passwordLogin: true`) while SMS cannot send for the moment (a company cap used up or the breaker paused: `sms_service.temporarily_unavailable()`).
- **Files.** `sms_service.py` (the pipeline: configuration and the placeholder rule, number validation, caps, circuit breaker, the log row), `twofactor_client.py` (the one HTTP call: 2Factor's custom-OTP call `GET {TWOFACTOR_API_BASE}/{api_key}/SMS/+{phone}/{otp}/{template_name}`; 5 s / 10 s timeouts, one attempt, redirects not followed, answer streamed up to 20,000 bytes, https only; **the key is in the URL, so it is redacted from every exception, log line (a filter on the urllib3 loggers), log row and answer**), `sms_control_views.py` (the HR API), `models/sms.py`, `otp_views.py`.
- **Environment** (`.env` only, never the database, the UI or a log): `TWOFACTOR_API_KEY`, `TWOFACTOR_TEMPLATE_NAME` (`UKT_HRMS_OTP`), `TWOFACTOR_SENDER_ID` (`UKTHRM`, informational), `TWOFACTOR_API_BASE`, `SMS_COUNTRY_CODE` and `SMS_ALLOW_SENDING`. A value that is empty, starts with `your_` / `your-` / `demo`, contains `yourkey` / `replace_me` / `changeme` / `xxx` / `todo`, is wrapped in `<...>` or contains `_here` / `-here` / `here_` / `...here` counts as not set (a real key that merely contains the letters "here" does not). A development machine (`DEBUG` or `runserver`) never sends SMS unless `SMS_ALLOW_SENDING=true`; `manage.py test` blanks the credentials.
- **Protections** (counted from `sms_message_log`, so they hold across workers and restarts; each send is reserved under a `SELECT ... FOR UPDATE` on the settings row): a circuit breaker (3 provider-side failed sends in 10 minutes pause SMS for 10 minutes; a refused number or one odd refusal does not count), company hourly (default 300) and daily (default 1,500, IST day) caps, a per-number cap (5 an hour), a per-employee resend wait (60 s) and hourly allowance (5), and wrong tries per code (5). All are editable on SMS Control within validated ranges (the hourly cap cannot exceed the daily one). **Switching SMS codes on is refused (400) until 2Factor is configured on the server.** SMS Control also shows the 2Factor balance (a read-only call, cached 5 minutes), this month's usage, delivery and used-code rates, and the estimated cost (price per SMS, default ₹0.20, and a monthly budget, both on Settings -> Cost). On a development machine `SMS_ONLY_TO_EMPLOYEES` limits every SMS to those employees' numbers. A refused request writes at most one `blocked` log row per employee per reason per minute.
- **Per-IP throttles.** `api/throttles.py` provides `@throttle("<scope>")` (placed under `@api_view`): the old `request.throttle_scope = ...` lines inside the views ran after DRF had checked its throttles, so nothing was ever throttled. The rates are now real: `login` 30/min, `employee_login` 300/min, `otp_request` 300/min and `otp_verify` 600/min per client IP (generous on purpose: a whole shop floor shares one address at shift start). A throttled answer is `{"error", "retryAfterSeconds"}` plus a `Retry-After` header. The client IP follows the `NUM_PROXIES` environment variable (default 1: the last `X-Forwarded-For` hop, the one Railway's proxy appends).
- **Tables** (migrations `0123_sms_otp_channel` and `0124_sms_default_caps` (the cap defaults 300 / 1500), additive, nothing seeded): `sms_settings` (singleton) and `sms_message_log` (never the code, the text, the key or a full number: the masked number, a keyed HMAC of the number, 2Factor's session id and one plain-sentence reason). Audit module `sms_control` (`update`, `test`).
- **Apps.** The mobile app (new APK / OTA) and the Employee Web App (its own deploy) read `otpChannels` / `channels`, use the one channel available automatically, let the employee choose when both are, remember the choice on the device, offer "send by the other way instead" after sending, and re-read the options whenever a screen gains focus or the app returns to the foreground. Older builds read only `otpChannel` / `codeLength` and send no channel, which keeps working.
- **Tests.** `api/tests_twofactor.py`, `api/tests_sms_otp.py`, `api/tests_sms_control.py`, `api/tests_otp.py`, `api/tests_otp_channels.py`, `api/tests_throttles.py` (2Factor is always mocked); browser: `frontend/e2e/sms-control.spec.ts` (incl. both channels on, each one alone) and `whatsapp-control.spec.ts`.

### 4.16 Endpoint Sharing (Settings → Endpoint Sharing)
The **super administrator** can publish chosen HR data to the company's other applications as read-only web addresses, `GET /api/shared/<slug>`. Everything is managed in **Settings → Endpoint Sharing** (group "Messages & data"); the sidebar is unchanged. It is **not** a role permission (no permission module): the backend gate `require_company_super_admin` looks the account up in the database on every call (active, `is_super_admin`, not tied to a branch) and refuses everybody else (an HR role with every permission, a branch login, an employee token: 403; no token: 401), and the Settings page does not list the tab for anyone else (`SUPER_ADMIN_ONLY_TABS`).

- **Files.** `models/shared_endpoints.py` (migrations `0122_shared_endpoints`, `0131_shared_endpoint_key_category`), `shared_datasets.py` (the catalog: a code whitelist), `shared_endpoint_views.py` (the public call), `shared_endpoint_admin_views.py` (the management API).
- **Datasets and fields.** `employees`, `departments`, `branches`, `designations`, `attendance-days` (stored daily verdicts; `dateFrom` and `dateTo` required, at most 31 days), `attendance-punches` (raw punches; required range of at most 7 days), `leave-requests`, `holidays`, `payroll-summary` (`month` required). A field is a catalog definition (key, label, type, **sensitivity**, columns, getter), never a model attribute named by a client; the row query loads only the columns of the selected fields (`.only()`), so an unshared column is not even read. Sensitivity levels: `basic` (organisation data), `personal` (phone, email, gender, date of birth, address, leave type / dates / reason) and `financial` (salary and payroll amounts). Saving an endpoint that newly selects a personal or financial field needs `acknowledgeSensitive: true` (otherwise 400 `sensitive_confirmation_required`, naming the fields); the change is audited with the field names. **Hard-excluded, never selectable** (a start-up error if a catalog name matches an excluded word): password hashes, tokens, OTPs, device secrets and API keys; Aadhaar, PAN and any government ID; bank names, account numbers and IFSC; PF / ESI / UAN numbers; photographs; biometric and device ids; HR user accounts, roles and sessions; every column that is not listed. An endpoint can **lock** filters (for example `status = active`, or `visibleToExternal = true` on employees) that a caller can never override.
- **The public call** (no HR login; `shared/` is in `EXEMPT_PREFIXES` of the permission middleware and `/api/shared/` is skipped by the global CORS via `CORS_URLS_REGEX`, because this route does its own CORS). Checks in order: the endpoint exists and is enabled (404 `not_found`, the same for unknown and disabled); the `Origin` header, if present, must be on this endpoint's list (403 `origin_not_allowed`), if absent the endpoint must allow server-to-server calls (403 `origin_required`); the key from `Authorization: Bearer <key>` or `X-API-Key` (never the query string) (401 `invalid_key`, the same answer for missing, unknown, revoked, expired and another endpoint's key); a per-key rate limit (429 `rate_limited` with `Retry-After`; default 60 a minute, 1-6000); filters, `page` and `pageSize` (400 `invalid_parameter` naming the parameter; an unknown or repeated parameter is a 400; `pageSize` is capped by the endpoint and the dataset). The answer is `{"data": [...selected fields only], "meta": {endpoint, dataset, category, fields, page, pageSize, total, hasMore, generatedAt}}` with `Cache-Control: no-store` (`meta.category` is `"staff"`, `"production"`, or `null` for an older key made before categories existed). A preflight `OPTIONS` from an allowed origin is answered 204 without a key; an allowed origin gets `Access-Control-Allow-Origin: <that origin>` on every response (never `*`, never credentials). **Origins protect browsers only: any non-browser caller can send any `Origin`, so the key is what protects the data.** The caller's address (log, failed-key limiter) is the last `X-Forwarded-For` hop.
- **Keys.** `uks_<8-character prefix>_<43 url-safe characters>`; only the SHA-256 is stored (the prefix is shown so a key can be recognised) and the plaintext is returned **once**, in the create response. At most 10 live keys per endpoint, 20 origins and 100 endpoints; revoking is immediate. After a failed key the caller's address is counted, so a key-guessing loop turns into 429. A key is made with `POST /api/shared-endpoints/<id>/keys` and a body of `{label, category, permanent | expiresAt}`:
  - **`category`** is required and is exactly `"staff"` or `"production"` (`""`, `"all"`, any other text or type is a 400). It is stored in `shared_endpoint_keys.category`. It is refused (400) when it contradicts the endpoint's locked `employmentType` filter (such a key would read nothing).
  - **The expiry is explicit**: exactly one of `permanent: true` (a real boolean; stored as `expires_at = NULL`, the key works until it is revoked) or `expiresAt` (a date `YYYY-MM-DD` = the end of that day in factory time, or an ISO date-time; a date-time without an offset is factory time IST). It must be in the future and at most 10 years away. Neither or both is a 400 ("Choose when the key expires, or make it a permanent key."). A string `"true"` for `permanent` is a 400.
  - The key JSON (create answer and list) carries `category` (`"staff"` / `"production"` / `null`) and `permanent` (true when there is no expiry). The audit row (`key_create`) records the category and `permanent` next to the label and prefix, never the key.
  - **Older keys** (made before categories existed) have `category = ""`: they keep working exactly as before and see **both** kinds of data (`category: null` in the JSON; the UI shows "All data (older key)"). They cannot be re-scoped: revoke and create a new key. New keys can no longer be made without a category.
- **Data categories, strictly enforced.** Category = `Employee.employment_type` (`staff` | `production`). After the key is accepted, `shared_datasets.apply_category(dataset, queryset, key.category)` narrows the dataset's queryset as one more `.filter()`, **before** `meta.total` is counted and before the page is cut, so nothing can widen it: not a query parameter (`employmentType=production` on a staff key is ANDed with it and returns zero rows, never the other category), not a locked filter, not `page` / `pageSize`, not which fields are selected; `meta.total` never counts the other category. An unrecognised stored category returns nothing (fail closed). Every dataset must declare how the category applies (`Dataset.category_scope` function **or** `category_neutral=True`); a dataset that declares neither (or both) is a start-up error, and a test pins it, so a new dataset cannot be added unscoped by accident. The admin preview (`POST .../preview`) takes an optional `category` and applies the same function.

  | Dataset | How the category applies |
  |---|---|
  | `employees` | the employee's own `employment_type` |
  | `attendance-days`, `attendance-punches`, `leave-requests`, `payroll-summary` | the `employment_type` of the row's employee (`employee__employment_type`; an inner join, so a row without an employee never matches) |
  | `departments`, `branches`, `designations` | only the rows that have at least one employee of that category (an `EXISTS` subquery, so no row is duplicated and paging stays exact), whatever that employee's status, so every `departmentId` / `branchId` in the category's employee rows resolves |
  | `holidays` | **neutral**: the company calendar holds no employee data, so a staff key and a production key both see every holiday |

  Payroll follows the employee's *current* type (the same rule as every other dataset): an employee moved from production to staff takes their old production payroll rows to the staff key.
- **Management API** (`/api/shared-endpoints...`, listed in `api-database-reference.md`): catalog, list / create / get / update (`PUT`, all-or-nothing, `expectedVersion` stale guard) / delete, keys (create, list, revoke), a preview (the first rows exactly as the public call shapes them; no key, no log row), activity, and a generated integration guide per endpoint (example code in six languages).
- **Access log and audit.** One row per call to a known endpoint (status, rows, origin, IP, duration, error code) in `shared_endpoint_access_logs`, kept 90 days (purged at most hourly); failure rows are capped per endpoint per minute. Audit module `shared_endpoints` (`create`, `update`, `delete`, `key_create`, `key_revoke`) with old and new values, never a key; `key_create` records the key's category and whether it is permanent. The access log has no category column (a call is attributed to its key, and the key carries the category).
- **Tables** (migration `0122_shared_endpoints`, additive): `shared_endpoints`, `shared_endpoint_origins`, `shared_endpoint_keys`, `shared_endpoint_access_logs`. Migration `0131_shared_endpoint_key_category` adds one column, `shared_endpoint_keys.category` (`varchar(12)`, default and `db_default` `''`, so the previous release can still insert keys during a rolling deploy; existing keys become `''` = unscoped).
- **Tests.** `api/tests_shared_endpoints.py`, `api/tests_shared_datasets.py` (the catalog, and that no excluded name can exist in it), `api/tests_shared_categories.py` (every dataset x both categories with staff and production seed data, adversarial query strings, locked filters, legacy and corrupted keys, the key-creation validation matrix, permanent and expiring keys against a moved clock, the preview); browser: `frontend/e2e/endpoint-sharing.spec.ts`.

### 4.17 PF, ESI & TDS (Co Emp, rules, TDS, coverage)
PF and ESI are no longer company-wide. They apply only to the employees HR switches on as **Co Emp** (Employees → Co Emp tab, `Employee.co_emp_enabled`), by rules the **Super Admin** keeps on **Settings → PF & ESI**; a separate **TDS** list holds the employees who have tax deducted at source instead. The whole model is one module, `api/pf_esi.py`, shared by both payroll engines, the Compensation page's employer cost, the coverage report and the settings API, so they cannot disagree. (Redesign of 2026-10-24; the API shapes are in `api-database-reference.md`, "PF & ESI, TDS and Co Emp".)

- **Categories (exactly one per employee).** *Co Emp* (`co_emp_enabled`): PF and ESI can apply; the employee is also visible in the CoPortal, exactly as before. *TDS* (`tds_enabled` plus `tds_percent`, above 0 and at most 100): TDS only, never PF or ESI; a TDS employee **stays visible in the CoPortal** (`pf_esi.COPORTAL_Q`, Co Emp OR TDS, is the scope of every CoPortal and "visible to an external application" query). *Neither*: nothing is deducted, ever. Co Emp and TDS exclude each other and the server enforces it in one transaction with the employee row locked: adding an employee to TDS (`POST /tds/employees`) switches Co Emp off, turning Co Emp on (`PATCH /employees/<id> {coEmpEnabled: true}`) takes the employee out of TDS, and removing from TDS leaves the employee in neither. If bad data ever carried both flags, TDS wins in the engine.
- **Rules.** Four independent lists: staff PF, staff ESI, production PF, production ESI (`PayrollSettings.staff_pf_rules`, `staff_esi_rules`, `prod_pf_rules`, `prod_esi_rules`, JSON, migration 0126). A rule is `{id, label, basis, minAmount, maxAmount, ratePercent}` and matches when `minAmount <= amount <= maxAmount` (both ends included, `maxAmount` 0 = no upper limit), where `amount` is the employee's FULL MONTHLY amount of the rule's `basis`: `basic` (the Basic component of the salary split, the default), `first_portion` (Basic + DA + Retaining Allowance) or `total` (the whole monthly salary; production: the monthly equivalent of the period's pay). The first matching rule in list order wins and no match means no deduction of that kind. Ranges of one list may not overlap (rules of different bases are not compared). Submitted lists are validated strictly by `clean_rule_list` (at most 50 rules a list, amounts 0 to 99,999,999.99 with at most two decimals, a percentage 0 to 100, unique ids) and a bad one is a 400 naming the list, the rule and the field.
- **Scopes.** *Global*: the four lists on the universal `payroll_settings` row, read by every login. *Unit-wise*: a branch can have a set of its own, a copy of all four lists inside `BranchSettingsOverride.overrides`, written only by `PUT /pf-esi-settings` (the generic settings API never touches them and `user_settings.persist_overlay` keeps them exactly as stored). A branch without its own set follows the global one; payroll resolves rules from the EMPLOYEE's branch (`settings_for_employee`), the settings page from the login's branch, so a branch login sees, read-only, exactly the rules its employees are paid under. **Only the Super Admin can write** (checked live in the database); `PUT` needs the `expectedVersion` content hash (409 `stale_version` when somebody saved first), `DELETE ?branchId=` returns a unit to the global rules, and every save is audit-logged (module `settings`) with the old and new lists.
- **Amounts.** PF or ESI = the matched rule's percentage x the FIRST 50% portion (Basic + DA + Retaining Allowance) of the period, prorated by attendance exactly as payroll prorates `basic`. **ESI uses the same base as PF now** (it used to be a percentage of all the pay earned). Staff are judged on their full monthly salary split (the recorded split, else the automatic one) and never on a part-month figure, so a short month cannot flip eligibility. **The automatic split gives Basic only one sixth of the salary** (the first half is shared equally by three components), so a rule "Basic below 25,000" covers salaries up to 150,000 unless HR records a split; for "salary below X" the rule's *Range based on* must be *Full monthly salary*. Production: eligibility is judged on the monthly equivalent of the period's earnings (Weekly x4, BiWeekly x2, Monthly x1, `production_cycles.MONTHLY_EQUIVALENT_FACTOR`) times the worker's split share of the chosen basis, and the deduction is the percentage of the first 50% of the period's earned pay. **TDS** = the employee's `tds_percent` of the EARNED GROSS of the period (staff: the pay earned plus overtime pay; production: the period's gross), rounded to 2 places, only for a TDS employee whose percentage is above 0. Worked examples: salary 20,000, Co Emp, PF 12% and ESI 0.75% rules that fit: full month PF 1,200 + ESI 75 (of the first portion, 10,000), net 18,725; 22 of 24 days paid: PF 1,100.00 + ESI 68.75. Salary 30,000 on TDS at 10%: TDS 3,000, no PF or ESI, net 27,000.
- **Payroll output.** `SalarySlip` and `Payroll` gained `tds_deduction` and `tds_percent` (the percentage used: a snapshot, so changing it later never rewrites an old slip). Staff `total_deductions = PF + ESI + TDS + advance + late` and `net = gross + OT - total_deductions`; production `net = gross - (PF + ESI + TDS + advance + late)`. A slip's `breakdown_details.deductions` keeps `pf, pfRate, esi, esiRate, advances, ...` and adds `tds`, `tdsPercent` and `statutory` (category, PF wages, the rule that matched with the amount it was tested on, the three eligibility amounts, rules scope, the TDS base and a reason). The old keys `esiApplicableBelow` and `pfEfRule` are no longer written; every reader (insights, Report Center, MD portal) also copes with slips stored before the redesign, which have no `statutory` block and no TDS (PF wages = `basic`, ESI wages = `gross_salary`). Any code that works out "late / other deductions" as `total - PF - ESI - advance` must also subtract TDS (`payroll_core_common.derive`, the Salary Statement and the MD analytics do).
- **Where TDS shows, and where it does not.** A **`TDS (10%)` line** appears only on documents of TDS employees: the salary slip (single PDF and the combined 2-per-page PDF; every other employee's slip has no TDS line at all) and the payroll Details page. Register-style outputs carry a **TDS column** that is 0 or blank for everybody else, so totals add up: the Salary Statement (staff and production, `others = total deduction - PF - ESI - TDS - advance`), the Report Center payroll registers, `GET /salary-slips` (`tdsDeduction`, `tdsPercent`), `GET /reports/payroll`. The Rules view of the insights pages lists the real PF and ESI rule lists of the scope (group "Statutory (PF / ESI)", linked to Settings → PF & ESI) plus a TDS note.
- **Report Center and MD portal.** The statutory statements read the stored slips and tell old slips from new ones: the **PF Statement** and **ESI Statement** take their wages from `deductions.statutory.pfWages` (PF and ESI now share the first-portion base) and fall back to `basic` / `gross_salary` for a slip stored before the redesign; the ESI Statement's coverage column says *Covered*, *Co Emp, no rule matched*, *TDS employee* or *Not Co Emp* (there is no "above the ESI ceiling" any more); the **PF / ESI Coverage Register** has a Category and a TDS % column and a category filter; the new **TDS Statement** (`tds-statement`) lists, per month, the employees with TDS on a slip (TDS %, TDS base, TDS deducted, totals); **PF / ESI Coverage** (`pf-esi-coverage`) is the live counterpart of the coverage endpoint. The salary registers, wage sheet, deduction summary, annual earnings statement and department cost carry a TDS column (0 for everybody else), and `payroll_core_common.derive()` / `LATE_SQL` subtract TDS before working out late and other deductions. The Payroll Controls check reads "total deductions = PF + ESI + TDS + advance + late". The employee **Statutory & KYC** report asks only Co Emp employees for PF, ESI and UAN numbers (nobody else can be charged them); numbers that are filled in are still format- and duplicate-checked for everyone. The MD portal's payroll pages show TDS as its own deduction line (never inside "other deductions" and not part of "statutory due", which stays PF + ESI + the employer shares), take the employer PF / ESI estimate bases from the stored `statutory.pfWages` (old slips: `basic` / `gross_salary`), and the AI assistant's `salary_slips` dataset has `tds_deduction` and `tds_percent` measures. The MD demo data (`seed_md_demo`) and the dev seed (`seed_data`) create Co Emp, TDS and plain employees whose slips are worked out with the real `pf_esi` functions.
- **Coverage: how many employees have PF / ESI deductions and how many do not.** `GET /pf-esi/coverage?type=staff|production|all&branchId=&detail=1` counts, per class, the active employees: total, Co Emp, with PF, with ESI, with both, with PF and/or ESI, Co Emp but no deduction (no rule matched), TDS, not Co Emp, and (production) not evaluated yet (`pf_esi.coverage_rows` / `coverage_counts`; staff are judged on their current salary split, production on the monthly equivalent of the latest generated period). `GET /pf-esi/coverage/export?format=xlsx|pdf&type=...&branchId=` downloads the same numbers (`pf_esi_coverage_export.py`): per class a summary block and one row per employee, one worksheet per class in Excel and one printable section per class in the PDF, as `attachment; filename="pf_esi_coverage_<type>_<YYYY-MM-DD>.<ext>"`. The Report Center has the same report as **PF / ESI Coverage** (`pf-esi-coverage`). Permission is the `employees` module and a branch login only ever gets its own branch. (DRF reads `?format=` as a renderer suffix and would answer 404 for `xlsx` / `pdf`, so the export view switches content negotiation off.)
- **Employer cost.** `ctc.ctc_figures` (Compensation page, CTC statement) uses the same rules: employer PF / ESI = the matched rule's percentage x the monthly first portion, 0 for an employee who is not Co Emp.
- **Data migration and rollout.** Migration 0127 converted whatever was enabled of the retired methods (flat rates, the ESI ceiling, the production salary bands, the "payroll rules" switches) into rules on the `total` basis and invented nothing where nothing was enabled; the old columns and the old `BranchSettingsOverride` keys stay in the database but nothing reads or writes them. **Rollout note: until HR switches Co Emp on for them, employees who used to get PF / ESI get none on the next generation. Stored payroll is never recomputed** (regenerating a month under the new rules is a separate, deliberate step).
- **Files and tests.** `pf_esi.py` (model, rules, arithmetic, coverage), `pf_esi_views.py` (`/pf-esi-settings`, `/pf-esi/coverage`), `tds_views.py` (`/tds/employees`), `pf_esi_coverage_export.py` (Excel / PDF), `reporting/definitions/pf_esi_coverage.py`, migrations `0126_pf_esi_tds_schema` and `0127_pf_esi_rules_data`. Tests: `api/tests_pf_esi.py` (rules, API, categories, engine, CoPortal, migration), `api/tests_pf_esi_outputs.py` (slips, coverage export, Report Center twin), `api/tests_payroll_insights.py` (details lines, Salary Statement, rules, settings links), `api/tests_reporting_payroll_statutory.py` / `tests_reporting_payroll_core.py` (statements and registers), `api/tests_md_payroll.py` / `tests_md_demo_seed.py` (MD analytics, demo data, dev seed).

### 4.18 On-Duty Geo-Tracking (api/geo_tracking/, migration 0132)

Our own tracking for staff on On-Duty work: no external platform, everything in seven new tables. It records the route, the **stationary (waiting / break) periods**, and every connectivity or integrity event (location off, network lost, app closed, phone shut down / booted, permission changed, fake GPS, battery), keeps them as history in the HRMS after the duty ended, and shows them in **Geo Attendance -> Journey History** (HR portal) and **My journey** (mobile app). The phone is a personal Android phone: the app records from a foreground service even when it is swiped away; a delayed upload is fine.

**Lifecycle (one track per On-Duty request).**
- **Starts** the moment the employee SUBMITS the request, before any approval: `on_duty_session_request` creates the `OnDutySession` and its `DutyTrack` in one transaction (`geo_tracking.sessions.start_track`) and writes a `TRACKING_STARTED` event. A second active track is never created (an active track whose session is over is ended first). If tracking is switched off, or the track cannot be created, the request still succeeds; the app's next `GET /tracking/state` creates the missing track for a session still in progress.
- **Ends only for four reasons**, all through ONE function, `end_track(track, reason)` (idempotent, first reason wins): `manual` (the employee marks the duty Done: `on_duty_session_complete`), `auto_4th_punch` (the 4th punch is captured: `_end_on_duty_session`; also HR approving the day's 4th punch of a still-active session), `auto_day_end` (the daily close, below) and `rejected` (a terminal rejection by the Department Head or HR in `resolve_on_duty_session`: tracking stops, **what was collected is kept**). `admin` exists for an administrator's manual end (no HTTP endpoint yet). **Approval never ends or changes the track.** Nothing else ends it (offline, app swiped away, battery). `end_track` closes the open interval events at `ended_at`, writes `TRACKING_STOPPED` and queues the final journey rebuild (a background thread started after the surrounding transaction commits; inline under the test runner). A failure to end the track never blocks the session close: it is logged and the scheduler's orphan check (every 2 minutes, `reconcile_orphan_tracks`) ends the track with the reason the session shows.
- **Day-end close at 23:50 IST** (was 23:00): `on_duty_day_end_scheduler.py` now runs a one-minute check job and closes the day ONCE per IST date, the first time the clock is at or past `GeoTrackingSettings.day_end_time` (default 23:50, validated 12:00-23:59), re-reading the setting on every tick so a changed time works within a minute without a restart; a server that was down at the time closes the day as soon as it is back. The close is the existing `end_stale_on_duty_sessions` path, so it ends the tracks too.
- After it ends the employee can submit a new request (a new track).

**Ingest: `POST /api/tracking/batch`** (employee token; `ingest.py`). Body `{deviceId, app, health, clientTime?, points[], events[]}`, camelCase OR snake_case at every level (the mobile app's axios decamelizes), times as epoch ms / seconds or ISO-8601 (a naive ISO time is read as UTC). Answer `{ok, ackSeq, accepted, duplicates, rejected, trackActive, endReason, serverTime, config}` (plus `acceptedPoints`, `acceptedEvents`, `rejectedReasons`).
- *Idempotent.* Every point and event carries a device-wide counter `seq`; `(employee, deviceId, seq)` is unique; a re-sent batch only raises `duplicates`. **`ackSeq` = the highest seq among the rows the server dealt with in THIS request** (stored, already known or refused for good); the app deletes its rows up to it, so it must send the queue in ascending order as one contiguous prefix. An empty batch acknowledges 0.
- *Per-row validation* (latitude -90..90, longitude -180..180, finite numbers, accuracy >= 0 and present, a usable seq and time; (0, 0) and times more than a day in the future are refused): a bad row is counted `rejected` (its seq is still acknowledged) and never fails the batch. Impossible optional values (a negative speed, a bearing of 700) are dropped, not fatal.
- *Which track.* The batch names none: each row goes to the track its TIME belongs to (a recording track takes everything from its start; an ENDED track still takes rows up to 5 minutes after `ended_at`, the offline queue; 2 minutes of slack before the oldest candidate's start). A row no track wants is rejected; an employee with no track at all (or tracking off) gets `trackActive:false`, `accepted:0` and every row acknowledged so the app drains its queue. Late data triggers a rebuild at once.
- *Consent.* Until the employee accepted the CURRENT notice version (`POST /tracking/consent {deviceId, noticeVersion}`; a stale version is 400 `NOTICE_VERSION_MISMATCH`) a batch is refused 403 `CONSENT_REQUIRED`. Per employee, any device.
- *Limits.* At most 500 points + 100 events and 1 MB per call: 413 `BATCH_TOO_LARGE`, nothing stored.
- *Cadence the phone follows* (`GeoTrackingSettings`, sent in `/tracking/state` and in every batch answer's `config`): a fix every `sample_moving_seconds` (3 s) while it moves and at least one every `sample_still_seconds` (**60 s**, was 300) while it stands still, a new fix otherwise only after `distance_filter_m` (10 m, or 0.8 x the accuracy if more). The 60 s still cadence gives a 3-minute stop three stored fixes and lets the phone notice a departure within a minute (about 60 rows an hour while still); the stop detection below also works on far sparser data, two fixes are enough.
- *Event pairing.* Interval events (`GPS_OFF`, `NETWORK_LOST`, `AIRPLANE_ON`, `POWER_SAVE_ON`) are stored open and closed by their END kind (`GPS_ON`, `NETWORK_RESTORED`, `AIRPLANE_OFF`, `POWER_SAVE_OFF`), which never gets a row: it closes the latest open interval of its kind at or before it (the closing seq is kept in that row's `meta.endSeq`, so a re-sent END is a duplicate); an END with no open start becomes a zero-length interval of the start kind (`meta.unpaired`); a second START while one is open is a duplicate. `SIGNAL_LOST` and `SERVER_NOTE` are server-only kinds (a phone sending them is rejected).
- *Clock.* A point more than 2 minutes in the future, or every row of a batch whose optional `clientTime` is more than 2 minutes from the server's, is flagged `time_suspect` (kept); the snapshot's `last_point_at` never goes past the server's now.
- *One transaction, short locks.* The employee's 3 newest tracks are locked with `select_for_update` for the length of the insert, so two concurrent batches (or a batch racing `end_track`) serialise and the counters (`F()` updates under the lock) stay exact. Points are inserted with `bulk_create(ignore_conflicts=True)`. The live snapshot (last position, battery, network, device) only moves forward; `TrackingDevice` and its health are updated; an open `SIGNAL_LOST` is closed. The journey rebuild is throttled to >= 30 s apart, runs after the commit, inline when the track has <= 800 points and in a background thread otherwise.

**The pipeline (`journey.py`, pure functions + `rebuild(track)`).** Parameters from `GeoTrackingSettings`. (1) *Clean*: sort by time then seq, drop duplicates, drop fixes less accurate than `max_accuracy_m`, drop teleports (implied speed > `max_speed_kmh`; a run of 3+ mutually consistent "teleports" is a relocation, not noise); mock-location fixes are KEPT and flagged. (2) *Stops*: a run of cleaned fixes that all stay within reach of the run's median centre for >= `stop_seconds` (up to two stray fixes tolerated). **R = max(`stop_radius_m`, `stop_accuracy_factor` x median accuracy) is the DETECTION radius** (it widens with poor accuracy); a fix is also judged against its OWN accuracy (inside when within max(R, 1.5 x its accuracy), at most 150 m), so one poor fix neither breaks nor shortens a stop. Two fixes at least `stop_seconds` apart and within reach of each other are a stop even with no fix between them (a phone that stores one fix a minute, or only a heartbeat). Also a run the phone calls `still`, and the two fixes either side of a gap that are within 75 m (the gap is part of the stop, flagged `estimated`); overlapping stops are one. **Then a stop that is really several SEQUENTIAL dwell places is split** (a first break, a walk of a few dozen metres, a second break), by evidence and not by a radius: the fixes are cut into TIGHT blocks (at least two fixes, every fix within max(25 m, 1.5 x its own accuracy) of the block's accuracy-weighted median centre, up to two strays skipped); consecutive blocks are one place unless they are SEPARABLE, i.e. their centres are more than max(25 m, 2.5 x (the two blocks' scatter added: the accuracy-weighted 75th percentile of a fix's distance from the centre), 0.9 x (the two median accuracies added)) apart; every place that lasts `stop_seconds` becomes a stop of its own, a place that does not (a pause of 2:50 before the real stop) goes back to travel, and a fix at the seam between two touching places goes to the place whose centre it is nearer to (a poor-accuracy fix belongs to the place it sits in). Two tight breaks 65 m (or 40 m, at accuracy 8) apart are two stops, 6-24 m apart one; a phone that flip-flops between two positions every minute, and a person drifting indoors with poor accuracy, are one stop; a return to the first place after a second break is a third stop. Stops less than `merge_stop_gap_seconds` apart are merged only when their cores are NOT separable (the same notion of "the same place", no longer "within 2R"). Then the EDGES are settled: fixes just outside a stop that are within reach of its stable centre are taken back (a run grows against a median that is still moving while it holds few fixes), and MOVING fixes at the start or end go back to travel: a fix the phone calls vehicle / bicycle / running, or whose step to its neighbour is longer than the GPS noise and 10 m and faster than 1.2 m/s, that lies beyond 0.6 R (and 1.5 x its own accuracy) from the centre and is farther out than its neighbour (an approach or a departure, not scatter). The stop starts at the first and ends at the last fix of the stable core, the centre and `radius_m` are computed on that core, and a core shorter than `stop_seconds` is no stop. Distance alone never trims a fix away, it takes movement (slow traffic that keeps moving is travel). A stop's walk to the next place is shared at its midpoint: a fix nearer to the neighbouring stop's centre is not taken back by this one. **A stop segment's `radius_m` is its SPREAD (the farthest fix from the centre: "the phone's positions stayed within X m"), not a detection threshold**; the radius used to detect it is `meta.detectionRadiusM` (= `meta.coreRadiusM`), next to `meta.fixCount` and `meta.centreAccuracyM` (the median accuracy of its fixes). (3) *Gaps*: more than `gap_seconds` with no fix outside a stop; cause from the overlapping events (device_shutdown > gps_off > permission > app_killed > network_lost > power_save > signal_lost > unknown); on a finished track, the time before the first and after the last fix is a gap too (flagged). (4) *Travel*: everything else; `distance_m` = the haversine sum of consecutive cleaned fixes inside travel segments (the straight line across a gap is NOT distance, it is in `flags.gapStraightLineM`); polylines are Ramer-Douglas-Peucker simplified (<= 400 vertices; the whole-journey `path` <= 1500). (5) *Summary*: distance, travel/stop/gap seconds, stop count, longest stop, top speed, first fix; the segments are one contiguous partition so `travel_s + stop_s + gap_s` is exactly the covered duty time (instants are whole UTC seconds). `rebuild` deletes and re-creates the segments and updates the summary in ONE transaction under the track's row lock; it is deterministic and idempotent and keeps addresses already looked up. A track whose raw rows the retention rule deleted (`flags.purgedAt`) is never rebuilt (its kept segments are all that is left).

**Live state** (`live.py`): `waiting_first_fix`, `moving`, `stationary` (inside an open stop >= `stop_seconds`), `offline` (no data for `signal_lost_seconds`, no open GPS_OFF), `location_off` (an open GPS_OFF), `ended`. The HR views overlay `offline` at once on a quiet track (`effective_state`); the stored state is refreshed by every batch and by the watchdog.

**Scheduler** (`geo_tracking_scheduler.py`, started by `apps.py`, never under the test runner): every 2 minutes the watchdog (`watchdog.run_watchdog`: orphan tracks, exactly one `SIGNAL_LOST` interval event per silent recording track, state refresh, the automatic tracking alerts (`alerts.run_alerts`, 4.27), the reverse-geocode worker); daily 03:30 IST the retention purge (`purge_old`: raw points and events of ENDED tracks older than `retention_days`; segments, the summary and the track stay). The reverse geocoder (`geocode.py`) is OFF by default (`reverse_geocode_provider = 'off'`: no coordinate leaves the server); with `nominatim` the scheduler thread fills stop addresses, at most 1 request per second, with a User-Agent, cached by a ~11 m grid cell, never inside a request.

**Two photos per On-Duty punch.** `OnDutyPunchVerification.photo2` (FileField, nullable). `GeoTrackingSettings.onduty_punch_photos` (1 until the new app is out, then HR sets 2): under 2, `POST /on-duty-sessions/punch` without `photo2` is 400 `{error: "Two photos are required: please update the app", code: "PHOTO2_REQUIRED"}`; under 1 an extra `photo2` is still kept. `GET /on-duty-sessions/status` (and `/attendance/geo-punch/status`) carry `requiredPhotos`, `/tracking/state` carries `punchPhotos`, verification dicts carry `hasPhoto2`, and `GET /on-duty-punch-verifications/<id>/photo?n=2` serves the second image (`n` absent or 1 = the first; other values 400).

**HTTP and permissions.** Employee (employee token; an HR token is 403): `GET /tracking/state`, `POST /tracking/consent`, `POST /tracking/batch`, `GET /tracking/my-journeys`, `GET /tracking/journeys/<id>` (own tracks only, 404 otherwise). HR (an employee token is 403): `GET /tracking/journeys`, `GET /tracking/journeys/<id>` (any track in the HR user's branch scope, else 404; **audit-logged**, module `geo_tracking`, action `view`), `/journeys/<id>/points` (cursor), `/journeys/<id>/trail` (every stored fix, compact, for the map; audit `view`), `/export?format=xlsx|csv` (audit `export`), `POST /journeys/<id>/rebuild` (audit `update`), `GET /tracking/live`, `GET|PUT /tracking/settings`. `permission_registry.URL_MODULE_MAP`: `tracking/journeys` and `tracking/live` -> `geo_attendance` (view reads, edit rebuilds), `tracking/settings` -> `settings.attendance` (no new permission key, so the mirrored lists in the apps need no change); a branch-limited login can READ the settings but not change them (company-wide rules). Full shapes: `api-database-reference.md`, section "Geo-Tracking".

**The On-Duty Map feed: `GET /api/tracking/journeys/day-map?date=YYYY-MM-DD`** (HR only, module `geo_attendance` view through the `tracking/journeys` prefix, branch scoped; `date` is an India calendar day, default today). Every journey that STARTED that day with its `track_head` fields and its `segments` (travel polylines, stops, gaps) in one answer, for the multi-employee map; the number of queries does not grow with the number of journeys. Not audit-logged (like `/tracking/live`: one `journeys/<id>` call per journey would write one audit row per journey on every 20 s refresh). Tests: `api/tests_geo_tracking_onduty_map.py`.

**Geo-punches in a journey (additive, for the employee app's On-Duty Journey page):** `GET /tracking/journeys/<id>` (employee and HR) gains `punches`: every `OnDutyPunchVerification` of the track's session ordered by punch number and creation time (a rejected punch that was redone appears twice): `id, punchNumber, punchType, punchDate, punchTime (IST wall clock), latitude, longitude, accuracyM, isMocked, hasPhoto, hasPhoto2, status, hrReviewComment, hrReviewedAt, createdAt`; the photos are not inlined (the app loads `/on-duty-punch-verifications/<id>/photo?n=1|2`). The journey list items (`my-journeys` and the HR list) gain `punchCount` (how many of the 4 slots hold a non-rejected punch; one extra query per page). Old clients ignore the new keys; an old server simply lacks them and the app hides punch counts.

**Route trail: `GET /api/tracking/journeys/<id>/trail`** (HR only, `@require_hr`, module `geo_attendance` view, branch scoped: 404 for an unknown or out-of-scope journey, 401 without a token, 403 for an employee token; audit `view`). Every stored fix of the track, compact, so the map can draw the COMPLETE route (a segment polyline is simplified and a stop is one pin): `{trackId, source: "points"|"segments", total, count, truncated, points: [{t, lat, lng, acc, spd, act, bat, net, prov, mock, used, stop}]}` in time order (`recorded_at`, `seq`). `t` = epoch milliseconds (UTC); `lat`/`lng` floats, 6 decimals; `acc` metres or null; `spd` km/h (1 decimal, the stored m/s x 3.6) or null; `act` still|walking|running|vehicle|bicycle|unknown; `bat` percent or null; `net` wifi|cell|none|unknown; `prov` gps|fused|network|passive|unknown; `mock` bool; **`used`** = false for a fix the cleaning step dropped (accuracy above `max_accuracy_m`, a teleport, an exact duplicate; same rule and settings as the pipeline), true otherwise; **`stop`** = the `seqNo` of the stop segment whose closed [`startedAt`, `endedAt`] holds the fix (the fix that starts or ends a stop belongs to it), else null (the numbers are those of the last rebuild). Over `MAX_TRAIL_POINTS` (8000) the list is thinned evenly, always keeping the first and the last fix, every fix whose time starts or ends a segment and every `used=false` fix (while they fit): `truncated: true`, `count` < `total`, still in time order. Once the retention rule has deleted the raw rows (`flags.purgedAt`) or they are otherwise gone the answer is built from the segments exactly like the detail's fallback `path` (every vertex of every travel polyline plus each stop centre): `source: "segments"`, only `t`/`lat`/`lng`/`stop` filled, `used` true and every other field null, so the endpoint never answers 500. Tests: `api/tests_geo_tracking_trail.py`.

**Privacy and safety.** Tracking only inside an active track; consent recorded per notice version (a changed notice text raises the version so everyone re-accepts); an employee sees only their own journeys; HR is branch scoped; every HR view of a journey is audit-logged; no third-party call by default (geocoder off); raw data is purged after `retention_days`; no token is ever returned.

**Device sessions (gates and desks).**
- A sign-in (`check_gate_login` / `check_desk_login`, then `start_gate_session` / `start_desk_session`) opens one `GateSession` / `ReceptionSession` row and returns a **30-day JWT**: `{"role": "gate_device", "deviceId", "gateName", "gsid"}` or `{"role": "reception_device", "deviceId", "deskName", "rsid"}`, where `gsid` / `rsid` is the row's random `sid`.
- **Why not `jti`:** `auth._authenticate` treats any `jti` claim as an HR `LoginSession` and would refuse (or mis-attribute) a device token; `gsid` and `rsid` also differ from each other so a gate token can never pass as a desk's.
- **Every request** goes through `auth.require_gate_device` / `require_reception_device`: the device must exist and be switched on (else 403 `gate_revoked` / `desk_revoked`) and the claim must name an open session of that device (else 401 `session_ended`). The session's `last_seen_at` is touched at most once a minute (one UPDATE). The views get `request.gate_device` + `request.gate_session` (or `reception_device` + `reception_session`).
- **Old tokens are refused.** Tokens without `gsid` / `rsid` (the 24-hour device sign-ins issued before this release) get 401 `session_ended`, so each gate and desk screen signs in once after the update (an old token had no session row, so HR could never have ended it).
- **Refresh:** `GET .../me` (the screens call it on load, every 5 minutes, when the tab is shown again and when the network returns) returns a fresh token for the same session once fewer than 15 days are left (`REFRESH_BELOW`), so a screen in normal use is never signed out.
- **Revocation** (`revoked_at` + `revoked_reason`): `logout` (Sign out on that screen: that session only), `password_changed`, `username_changed` (not for a change of letter case only: usernames match case-insensitively), `deactivated` (switched off), `hr_signed_out` (HR "Sign out everywhere"). The first four come from `PUT .../<id>`; deleting a device cascades its sessions. "Signed in now" on the HR pages = an open session seen in the last 10 minutes (`SIGNED_IN_WITHIN`); a session counts as live only while its token could still be in use (seen within 30 days).

**Sign-in and the lock.** One shared sign-in per kind (`POST /api/gate-monitor/login`, `POST /api/reception-devices/login`, both `@throttle("login")`): the username, matched case-insensitively, decides the device. Every attempt is a row of `gate_login_attempts` / `reception_login_attempts` (username trimmed and lower-cased, IP, success; never the password; nothing recorded for an empty username, which is a 400 `missing`). The lock: when the last 5 attempts for a username within 15 minutes were all wrong, further attempts get 429 `locked` until the window passes; only attempts after the device's `updated_at` count, and every HR save stamps `updated_at`, so an HR password reset (or any other change) unlocks it at once. A correct password for a switched-off device is refused (403 `switched_off`) and counts as a failed attempt. Answers: 401 "Wrong username or password.", 403 "This gate is switched off. Ask HR to switch it on." / "This desk is switched off...", 429 "Too many wrong tries. Wait 15 minutes or ask HR to reset the password." The old kiosk `POST /api/gate-devices/login` shares `check_gate_login` (same lock, a session token, its old keys and its old 401 wording).

**Passwords and the encrypted copy.**
- `password_hash` (bcrypt, 10 rounds) stays the only sign-in check. Beside it `password_encrypted` keeps the same password Fernet-encrypted so HR can be shown it. The Fernet key is `urlsafe_b64encode(sha256("uktex-gate-password:" + settings.JWT_SECRET))`, shared by gates and desks.
- **Rotating `JWT_SECRET` makes every stored copy unreadable** (and ends every HR, gate and desk sign-in). Sign-in keeps working (bcrypt); View password then answers 409 `not_stored` until HR sets a new password. Passwords set before 18 Nov 2026 have no copy (`password_encrypted` NULL, `passwordViewable: false`) for the same reason: only the one-way hash was kept.
- Create and reset go through `set_gate_password` / `set_desk_password` (hash + copy in one place; they never revoke on their own: the PUT revokes). Length rules: username 3-60 characters without spaces, password 6-128.
- The copy is decrypted only by `POST .../<id>/reveal-password` (answer `Cache-Control: no-store`), never in a list, detail, export or log. Every reveal is an audit row `view_password` on module `outpass_visitors` (shown in Activity Logs, and on the MD's activity page as the high-severity rule `gate-password-viewed`); the password itself is never logged.

**The reveal keys fail closed.** `outpass_visitors.outpass.gate_devices.view_password` ("See gate passwords") and `outpass_visitors.visitors.reception_devices.view_password` ("See desk passwords") are the only keys of the tree that do **not** follow their parent: a role that has nothing set on them is refused (an Edit on the whole Outpass / Visitors section, or on "Gate scanner devices", is not enough). A role must be given the key explicitly. The Super Admin always has them; the MD's working access (`permission_registry.MD_HR_GRANTS`) deliberately does not include them. The screens only offer View to accounts that hold the key.

**What a gate scans.** `GateDevice.allow_outpass` / `allow_tea_break` (default both on). `resolve_gate_scan` refuses a recognised code of a kind the gate does not take with 403 `{result: "not_allowed_here", kind, message}` (plus the employee / pass details) and writes a denied `OutpassGateScan` row (`result = not_allowed_here`): a pass keeps its exit / entry `scan_type`; a refused tea-break code is stored with `scan_type = "tea"` (migration 0164), so every reader (gate records, the Report Center's gate reports, the MD analytics, the In/Out scan log) shows it as a denied tea-break attempt and counts it under Denied, never as an exit. An unreadable code is still `invalid_qr`.

**Gate records (`gate_records.py`).** One list of everything that happened at the gates, from three sources merged in SQL (`values()` + `UNION ALL`, ordered by time, paginated): every `OutpassGateScan` (exit -> `exit`, entry -> `return`, allowed or denied; `tea` -> a denied `tea_out`), each `TeaBreakLog` out scan (`tea_out`) and in scan (`tea_in`). Days are IST (`gate_visitor_tea_common.ist_bounds`, never `__date`). Branch is the **gate's** branch (not the employee's); rows of a deleted gate (gate NULL, shown as "Removed gate") reach only HR accounts not bound to a branch and with no branch filter. Photos are signed links. A page costs a fixed 8 queries; `pageSize` is capped at 100. `records_page`, `record_counts`, `records_for_export` (at most 30,001 rows read), `params_from_query(allow_gate=False, allow_branch=False)` for the gate monitor (which always passes its own gate only), `gate_counts` / `gate_last_activity` / `gate_summary` for the tiles and the per-gate numbers (grouped queries, never one per gate). Bad input raises `BadParam` -> 400.

**Files (`gate_exports.py`).** `file_response(request, slug, title, columns, rows, fmt, filters_text, summary, notes)` builds the Report Center's own input objects and calls `reporting/export_xlsx.build_xlsx` / `export_pdf.build_pdf` with the letterhead, so every file looks like a Report Center file. A page builds its own rows (its own filters and permission key); this module only writes. Row limits as in the Report Center: 30,000 (Excel), 5,000 (PDF), above that 413 `too_many_rows` and no file; a bad `fmt` is 400 `invalid_format`; a writer failure 500 `export_failed`. Filename `<slug>_<YYYYmmdd_HHMM>.<ext>` (IST), `no-store`, audited `export`. No file holds a password, a hash, a login link, a pass QR code, a full Aadhaar number (only `XXXX XXXX 1234`), and the desk records file holds no phone number either.

**Visitors.** A visit's status is derived, never stored (`checked_out` / `inside` = today and not checked out / `not_checked_out` = "Left without check-out"). `register_visit` is the one check-in path for HR (`source "hr"`) and the desk (`source "reception"`, `checked_in_desk`): the phone finds a returning visitor (exact text, then the last 10 digits however typed), a visitor still inside at that branch is 409 `already_inside`, the host must be an employee of the visit's branch, and the host message (email + WhatsApp) is best effort. A check-out is recorded once, up to 24 hours after check-in (a visitor still inside after midnight can still be checked out), by HR or by the desk of that branch (`checked_out_desk`, `checkout_source`). `minutesInside`, the average and the files use one rounding rule.

**Branch scoping.** A branch-limited HR account sees only its own branch everywhere in this area: gates and desks (another branch's is 404, never shown), gate records (by the gate's branch), In/Out (by the employee's branch), visits and the visitors directory, tea breaks (by the employee's branch); a `branchId` it sends is ignored, and it can only create or move a gate / desk into its own branch (403 otherwise). A reception desk is always limited to its own branch: its lists, files, check-outs, the returning-visitor look-up and the visit counts it is shown never include another branch's visitors.

**Permission keys** (`permission_tree.py`, `permission-inventory.md`): `outpass_visitors.outpass.gates` (tab Manage Gates, screen only, inherits `outpass_visitors.outpass.gate_devices`), `outpass_visitors.outpass.gate_devices.view_password` and `outpass_visitors.visitors.reception_devices.view_password` (fail closed, above), `outpass_visitors.visitors.visits` and `outpass_visitors.visitors.desks` (tabs; Manage Reception inherits `outpass_visitors.visitors.reception_devices`); new API prefixes `outpass/in-out` (on `.outpass.in_out`, moved off the Requests module) and `visitor/visits`, `visitor/people`, `visitor/export` (on `.visitors`). ### 4.20 Compensation claims: one workflow for every kind (2026-11-19, migration 0166)

**One claim table.** `HolidayWorkClaim` (table `holiday_work_claims`, every old column kept) is THE claim of every kind: `kind` = `holiday_work | ot_allowance | ot_shift | birthday | use_balance` (`db_default` `holiday_work`, so every old row and every row an older release inserts during a rolling deploy reads as the holiday-work claim it is), `work_date` = the claim's date for every kind (the work day, the OT date, the birthday, the day off), `shifts`, `overtime_record` (FK `OvertimeRecord`, SET_NULL, ot_* kinds) + `minutes` (ot_allowance: the allowance minutes detection granted), `raised_by_role` (`hr | employee`, `db_default` `hr`). **compensation_effects.** `after_claim_decided`: an approved `ot_allowance` re-derives the next working day after the OT date through `compute_range_records` (only when that day has come, is not in a locked / Payroll Done month; a manual day is returned untouched by the engine); an approved `use_balance` calls `compensation_apply.apply_relaxation` (the ledger debit is what the engine tops the day up from); credits and rejections change no attendance. `check_claim_effects` (before approving and, for `ot_allowance` / `use_balance`, before creating): Type 1 needs a following working day that is not in a locked month and, when it already happened, not set by hand; a use request needs `check_relaxation_day` (a working day, not already a full paid day, at most 1.00 in all) and an unlocked month.

**Effective dates (no history rewrite).** `CompensationConfig.claims_from` (data step: the IST day 0166 ran; NULL on a row created later = every day) and `claims_apply_on(day)` decide per date: an OT day, a birthday or a holiday on/after it follows the claim rules, an earlier one keeps the old rules even when recomputed. Payroll is never regenerated by any of it; re-derivation only through the existing refresh paths, never for manual days or locked months.
- **Type 1:** before `claims_from` automatic (the engine derives the allowance from the previous working day's extra work). From it, `compensation_engine.allowance_for_arrival` grants an allowance ONLY through an approved `ot_allowance` claim for that OT date (`CompContext.allowance_claims`, one query in `build_context`, none when the whole range is earlier). An unclaimed `auto` record stays as a record. The employee app's `todayAllowance` / `tomorrowAllowance` show approved allowances only.
- **Type 2, the quarters rule** (`CompensationConfig.ot_quarter_rule`, default on): `compensation_rules.quarter_credit(extra, shift_minutes)` = whole quarters of `extra * 4 // working minutes`, capped at 1.00 (integer arithmetic: 120 of 480 is exactly 0.25, 119 is 0); `working_minutes` / `compensation_engine.shift_working_minutes` = end - start (overnight ends the next day) - lunch. `overtime.classify_day`: from `claims_from` with the rule on and a known shift, a day reaching a quarter is Type 2 (`detected`, the credit as `suggested_shifts`), below a quarter Type 1 by the allowance rows with no Type 2 threshold; otherwise the old threshold + last-punch ladder. Detection never updates or prunes a record that has a claim of any status (snapshot check plus `Exists()` in the conditional writes).
- **Pay vs credit guard:** HR may still Pay a Type 2 record (pay switched on), but `overtime_assign` / `announce` / `reject` skip a record with a pending / approved claim (assign answers 409 `claim_conflict` when every record is claimed), relaxation is refused for records on/after `claims_from` (their credit is the claim), and a claim / approval is refused for a record HR already decided. A worked birthday is a normal day plus one 1.00 credit to claim. **Provisional today:** a birthday that is today with no punch yet is NOT made birthday leave; it is stored with `provisional_until` = next midnight IST, so `attendance_refresh.refresh_provisional` works it out again the next day (then paid leave if nobody punched); `birthday_outcomes` reports it as `upcoming`, and re-computes a stale stored absent / on-leave day (or a birthday-leave day that has punches now) before answering. `birthday_applies` (old rule only) keeps its meaning for its callers; `attendance_views`, `compensation_apply` (`_birthday_leave_on`: any rule) and the reports follow `birthday_rule`.
- **CL policy (2026-11-21):** `CasualLeavePolicy` (Settings -> Casual Leave; `casual_leave_views.casual_leave_settings` = `GET|PUT /api/casual-leave-policy`) drives `cl_balance.py`: `Policy` (frozen; `policy()` read-only, defaults when no row), `eligible_from(joined, pol)` months|days, `YearLedger` (`available(month)`, `given_through`, `left_at_year_end`, `carried_out`), `ledgers(ids, year, cut_over, pol)` (2 queries + earlier years when days move into the next year), `balance_json(ledger, cut_over, today)` (NEW signature), `available_on(emp, d)`. `check_cl_eligibility` = staff + active + `service_refusal` (policy, judged today) + half-day switch + `_check_yearly_balance` (the date's month). No extra query unless a date of birth matches a CL date.

**Staff next-morning cut-off** (`shift_engine.py`, decision 5, like production's 06:00): a staff punch on day D+1 strictly before `PayrollSettings.staff_next_morning_cutoff` (default 06:00) belongs to day D (the end of D's overtime, measured from D's shift end) when D's OWN punches leave a session open (an odd count); every early punch of D+1 goes with it; from the cut-off on a punch is D+1's own. "Own punches" = D's punches minus those D-1 took the same way, so a run of early punches is followed back (`_StaffNight`, memoised, at most `STAFF_NIGHT_CHAIN_DAYS` = 10 days; one day, a range and a month agree). **Per pair of days:** (D, D+1) follows the rule when `staff_next_morning_enabled` and D >= `staff_next_morning_from` (`staff_next_morning_applies`, read field by field so a branch overlay works); an earlier pair, or the switch off, keeps the old `last_punch_post_shift_grace_hours` rule exactly. ### 4.27 Automatic On-Duty tracking alerts (2026-11-21, migration 0175)

Owner brief: while an employee is On-Duty the HRMS detects tracking problems by itself and tells the employee (WhatsApp + phone notification), then their Department Head when it is not fixed. Code: `api/geo_tracking/alerts.py` (detection, episodes, both channels), `api/geo_tracking/alert_views.py` (HR log), called at the end of `watchdog.run_watchdog` (every 2 minutes, after SIGNAL_LOST and the states; one gunicorn worker + `max_instances=1`, and the partial unique index below makes a double run harmless). Tests: `tests_geo_tracking_alerts.py` (36).

**The six kinds (rules as built, default timing):**

| Kind | Detected when | Employee told | Department Head |
|---|---|---|---|
| `location_off` | an open GPS_OFF event on the track, or the phone's health says location disabled | 2 min after it began (debounce) | 15 min after the employee's alert, if still off |
| `permission_restricted` | the track's phone (the one that sent the last fix, else the one seen most recently since the track started) reports permission `while_using` / `denied` (`unknown` never alerts) | 2 min after first seen | + 15 min |
| `background_restricted` | that phone reports `background_restricted` or `battery_optimised` | 2 min after first seen | + 15 min |
| `tracking_failure` | the watchdog's open SIGNAL_LOST (no data for `signal_lost_seconds`, 10 min; also a track whose phone never sent anything) | at once (the silence was the wait) | + 15 min |
| `missing_punch` "first" | no punch of the day (any source, a pending On-Duty punch counts: `_taken_slots`) 30 min after the track started | at once | + 15 min |
| `missing_punch` "day" | 1-3 of the day's 4 punches at the punch check time (19:00 IST) while a duty begun before it records, or when the employee marks it Done (0 punches too, when the "first" alert never went) | at once | + 15 min, while the day still lacks punches |
| `punch_reminder` | no punch for 180 min while on duty (from the day's last punch, or the track start if later), a slot still free, no Missing Geo-Punch open | at once, ONE per wait | never |

**Episodes** (`GeoTrackingAlert`): one open row per (track, kind, key) (partial unique index `uniq_open_geo_alert`); stages claimed with conditional UPDATEs (exactly once); cleared -> `resolved_at`, `resolution` fixed (an episode never alerted, a blip inside the debounce, is deleted); the track ends -> `track_ended` (a "day" missing punch stays open until 4 punches = fixed, or the IST day is over = `day_over`); the same phone-state problem again within the cooldown (30 min) reopens its episode (no second alert), later it is a new one; missing-punch / reminder keys are used once per track; alerts switched off -> every open episode `alerts_off`. A kind that NO channel would carry (Phone Notify Control master/kind off AND WhatsApp off or not configured) is not tracked at all.

**Timing** lives in Geo Attendance -> Settings (`GeoTrackingSettings`, `tracking/settings`): `alertsEnabled` (true), `alertDebounceMinutes` (2, 0-30), `alertHodEnabled` (true), `alertHodGraceMinutes` (15, 1-240), `alertCooldownMinutes` (30, 0-720), `missingFirstPunchMinutes` (30, 5-240), `punchCheckTime` ("19:00", 12:00-23:59), `punchReminderMinutes` (180, 30-720). The silence time is the existing `signalLostSeconds`.

**Channels, each with its own settings only** (owner 2026-11-17/21, modules independent): the detection hands each stage to both at one call site.
- Phone (Phone Notify Control): six kinds in `mobile_messages.TRACKING_ALERT_TYPES` (group `tracking` "On-Duty tracking alerts", category `on_duty`, audience `employee_hod` / reminder `employee`), default ON like every push kind; wording `push_templates.APP_SPECS` (`{{headline}}` / `{{message}}` = the built-in title and sentence for whoever receives it, plus `employee_name`, `employee_code`, `recipient`, `recipient_name`, `destination` and the kind's details). Recipients mode (an excluded employee gets nothing: outcome `not_recipient`), master / kind switch (no row made), per-employee mute (row made, push "off" at push time). Notification `type "on_duty"`, `source` = the kind, `dedupe_key "geoalert:<alert>:<stage>:<session>"`; `notification_targets` opens the employee's On-Duty screen at the session, the head's Approvals -> On-Duty at it. The mobile app needed no change (type `on_duty` and both target kinds exist).
- WhatsApp (WhatsApp Control): catalog module `geo_alerts` "On-Duty tracking alerts", six employee types + five `*_hod` copies (`MessageType.escalation_of`: they follow their type's switch and are never a switch of their own), templates `hrms_<type>`, kind automatic (paced queue, quiet hours, per-employee cap, opt-out, the dev machine's `WHATSAPP_ONLY_TO_EMPLOYEES` lock), fresh 30 / 60 min. ## 6. Attendance Engine In-Depth

Lives in `shift_engine.py` and `attendance_final.py`; every threshold below is HR-editable in Settings → Attendance/Late Detection (`PayrollSettings` model) -none of it is hardcoded, so the same codebase serves any company's policy without a code change.

**Current staff arrival rules (supersede the older punctuality-window text below where they differ):** the first punch is placed on the *arrival timeline* of the employee's own shift (`arrival_rules.py`): on time to start + grace, **Late** for `arrivalLateWindowMinutes` (60, Full Day + one late-pool occurrence), then the permission window (`arrivalPermissionWindowMinutes`, 60: an approved in-cap Morning Late-In permission excuses up to here, otherwise a **quarter shift**), then `arrivalExtraMinutes` (20: quarter shift, never covered by a permission), and after that the first half is missed: **Absent until a punch at/after Second Half Start, then Half Day**. A quarter-shift arrival earns `1 - arrivalQuarterDeduction` (0.75), is not also Late, and is not docked twice if the day is already a Half Day. All four numbers are Settings → Attendance; the fixed First Half End time is retired. See `attendance_final.compute_day_record`.

**Full vs Half Shift (staff, both modes):** Full only when a first *and* distinct last punch both fall within the **Shift Punctuality Window** (`shiftPunctualityWindowMinutes`, default 60 min) of the assigned shift's start/end. Anything else with ≥1 punch is Half Shift; zero punches (and not on leave/holiday) is Absent. No assigned shift ⇒ no reference, so no late flag either.

- **Half Shift Late Reference:** on a Half Shift day, "Late" is decided purely by whether the first punch is after a separate configured time (`halfShiftLateReferenceTime`, default 2:30 PM).
- **Night Shift Relaxation:** can upgrade a punctuality-caused Half Shift back to Full for employees who worked late the previous night.
- **Cross-midnight punch reattribution:** a forgotten evening exit punched after midnight is reattributed back to the correct shift-day within a configurable grace window, instead of corrupting the next day's punch order. From `staff_next_morning_from` (2026-11-19) the **staff next-morning cut-off** decides instead: a punch before 06:00 (setting) ends an open day before as its overtime, with an early-arrival guard from the next shift's start (Section 4.20); earlier days keep the grace window.

**Strict vs Simple (staff):** both share the Full/Half decision above. Strict additionally tracks lunch-return lateness (a first-half-end window locates the lunch punches). Simple only looks at first/last punch.

**Late Detection pool (Settings → Late Detection → Late Attendance):** plain lates + Half-Shift-day lateness + strict-mode lunch-return lateness + approved Permissions all feed **one shared monthly pool**. First `lateFreeAllowance` (default 3) are free; every occurrence past that is billable, priced by an HR-editable slab table. Empty table = no penalty.

**Permission Deduction Slabs (Settings → Late Detection → Staff; staff only, switch OFF by default, added October 2026):** by default an *excess* permission (an approved one beyond `permissionMonthlyCap`, counted over the whole calendar month and all three types together) is one mark in the late pool above. With `permissionPricingEnabled` ON the excess permissions **leave** the late pool (the pool is then Morning Late-In + Evening Early-Out only) and are priced on their own, the way the late pool is: the first `permissionFreeAllowance` (0-999) of them are free, the rest are *billable permissions*, priced by `permissionDeductionSlabs` (`[{fromPermissions: whole 1-999, deductionShifts: 0-31 with at most 2 decimals}]`, at most 50 rows, stored ascending with duplicate thresholds removed; the highest row reached wins, the last row holds beyond itself, an empty table deducts nothing). The lookup is the late slabs' own: `payroll_views.permission_shift_deduction` plugs the table into `late_shift_deduction`'s `slabs=` hook with `fromPermissions` handed over as `fromLates` for that call only (the stored settings are never changed). Penalty = shifts x daily rate, rounded half-up. A new payslip carries it as its own line, `deductions.permissionPenalty` plus `deductions.permissionSummary {enabled, approved, cap, excess, absorbedByLate, priced, freeAllowance, freeUsed, billable, shifts, penalty}`, and it is added to total deductions, `SalarySlip.other_deductions` and the net exactly like `lateShiftPenalty` (all additive keys; stored slips are never touched). **Never twice for one incident:** a day that is late (or early) AND carries an excess permission on the same edge stays ONE incident, counted in the late pool (`late_in` / `early_out` then include it), and that permission is *absorbed*: it is not priced again. So `excess == absorbedByLate + priced`, and (late pool total + priced permissions) is always the pool total the OFF formula would give. Only present / half-shift days on payroll working days can absorb a permission (a flagged Sunday absorbs nothing, its permission stays priced); the excess count itself stays the whole month, as it always was. The ONE shared pair of functions is `attendance_final.late_pool_summary` (the counts) and `payroll_views.late_pool_pricing` (shifts and rupees); payroll, `MonthlyShiftSummary` (its `shift_deductions` / `salary_deduction_amount` hold the TOTAL late + permission, which is all the installed My Shift screens read), the employee shift-stats preview (additive `permission*` keys in `summary` and `policy`), the late and permission reports, the payroll insights (`permission_penalty` deduction line, `excess_permission` issue, three rule items) and the MD demo data all call them, so they cannot disagree. OFF (the default) reproduces the old numbers to the paisa (pinned against a verbatim copy of the old formula in `tests_permission_slabs.py`). Production permissions are never priced. The three keys are company-wide (`COMPANY_WIDE_RULE_KEYS`: a branch login gets 403 `company_wide_rule`; `user_settings.COMPANY_WIDE_FIELDS` also makes the settings overlay ignore a stray branch value) and belong to the `settings.late_detection` permission group; switching ON with an empty table is refused (400 "Add at least one permission slab before turning this on."). **Production is never priced by any caller:** `shift_engine.compute_monthly_shift_summary` prices permissions only for `employment_type == "staff"` (a production summary is the same with the switch ON or OFF), the shift-stats preview reports pricing OFF with an empty slab table for production, and the reports build no pool for production. The HR recompute (`POST /api/attendance/compute-shifts`) works on staff only and passes payroll's ROUNDED daily rate (`_d2(salary / working days)`), so the recomputed `salary_deduction_amount` equals the payslip to the paisa. **Slab input is validated, never a 500:** `clean_permission_slabs`, the staff and production late slabs (`payroll_views._clean_late_slab_rows`) and the per-cycle late rules (`production_cycles.clean_slabs` / `merge_prod_cycles`) accept only plain numbers (text such as `1_0`, `1e1`, `nan`, `inf`, Unicode digits or a digit string beyond Python's int limit, true / false, 1e999 and 2.5 lates are refused with a 400 and nothing is saved); late slabs also stop at 999 lates and 31 shifts.

**Without Permission detection (Settings → Late Detection → Without Permission):** a separate, independent pool covering the narrow zone between the shift's grace period and the wider punctuality window (morning late-in and evening early-out, mirrored). An approved Permission near the relevant shift boundary suppresses it; without one, the day is flagged "Without Permission." Ships with **0 free allowance and an empty slab table** (zero payroll impact until HR explicitly configures it) -deliberately independent from the Late Attendance pool so nothing double-counts.

**Production attendance:** a separate segment-based engine (`ProductionShiftConfig`/`ProductionShiftSegment`) -each configurable punch window earns its own shift fraction. Sunday is a normal working day.

**Production shift rules (October 2026):** from `ProductionShiftConfig.rules_effective_from` a production day is judged by the groups, ladders, unpaid breaks and 5-minute grace of `production_shift_rules.py` (Day / Night / Sunday, night sessions closed by the next morning's punch, up to 3.00 shifts a day); earlier days keep the segment engine above. See the "Production shift rules (October 2026)" bullet in 4.7.

## 9. Backup & Restore

`backup_service.py` / `backup_views.py` / `backup_scheduler.py`. A backup is one zip: `db.sql` (plain `pg_dump` SQL) + `manifest.json` (timestamp, row counts for a few headline tables) + a full copy of `MEDIA_ROOT`. Restore is a full, reliable replace (`DROP SCHEMA public CASCADE` → reload) -not a row-level merge, deliberately (see `deployment-guide.md` for the reasoning). Validation now compares a candidate backup's row counts against what's currently live and warns in the UI if restoring it would discard newer data; a fresh safety backup of the current state is always taken automatically immediately before any restore runs, so a bad restore is always undoable. Cloud-Postgres readiness (SSL mode, timeouts, a clear error on a schema-ownership failure) is covered in `deployment-guide.md`/`clouddeployment.md`.

## 12. Known Limitations

- **Weekly-off is hardcoded to Sunday** for staff -not configurable per branch/unit yet.
- **Legacy leftovers:** `SessionConfig`/`WorkSession` models, `prod_first_half_*` `PayrollSettings` fields, (the "Legacy Session Config" panel on Staff Payroll was removed 2026-11-10; its endpoints remain) exist only to keep old session-based records viewable. Safe to remove once those old records no longer need viewing.
- **Legacy `SalaryRecord` auto-calc** (`÷26` monthly / `÷6` weekly, in `views.py`) is superseded by the real payroll engine -a removal candidate.
- **Production employees without `salary_per_shift` are skipped at generation**, by design -reported clearly in the Skipped Employees list.
- **Biometric device Comm Key** can't be validated against the device itself from the UI -a wrong value is only caught when a sync actually fails.
- **PF / ESI coverage for production is a prediction.** A production worker's pay changes every period, so the coverage report judges a Co Emp worker on the monthly equivalent of their latest generated period (no payroll yet = "not evaluated"); the real deduction is decided when each period is generated.
- **Slips stored before the PF & ESI redesign keep their old basis** (ESI as a percentage of all earned pay, PF from `basic`, no TDS) and are never recomputed; the Report Center statements show both kinds side by side.
